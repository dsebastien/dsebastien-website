# Publish Notes

The publishing tool of the notes website takes notes of the vault to the content store, from which the site is built. An agent drives it through operations that have the same name and the same output on every face: `status`, `plan`, `publish`, `unpublish`, `takedown`, `unlock` and `confirm_store_state` for the publications, `deploy` for the site, and `guards`, `deny`, `allow`, `ignore` and `unignore` for the guards. After its push, a publication, an unpublish and a takedown deploy the site on this machine. The tool holds every rule; this skill says how to use it the way the author wants.

## Critical Rules

1. **Publish alone only new versions of published notes.** The notes of the list `changed` can go without a question when the author asked for a publication. A new note (`include`), an unpublish (`remove`, `unpublish`), a pairing (`pair`) or a takedown happens only for a note that the author named in this conversation, because a published note is public at once and a selection error is a privacy error.
2. **Show the plan before a publication that does more than updates, or that has edits of the guards.** Give the lists of the plan (new, updated, unpublished, moved, forced removals) and wait for a yes. The id of the plan goes to `publish` unchanged. When `edits` is not empty, give each event (action, path, state) to the author before `publish`: the plan is where the author sees the edits of the guards. A plan with `forcedRemove` or `guardedAttachments` (published notes that would lose a file under a guard) publishes from an agent only when `accept` names each of those paths: give them to the author, and add them to `accept` only when the author says yes for those notes. Else the author publishes that plan in the publication center.
3. **A guard wins, and an agent edits it only through the tool.** Never write `publish_ignore` into a note, or `configuration.json` into the copy, yourself: the tool logs each edit, and the plan shows it to the author. `deny` and `ignore` make the guards stricter and apply at once, unless they take away a manifest entry (a published or an unpublished note). `allow` and `unignore` are always proposals, and only the author confirms them, in the publication center. Never call `allow` or `unignore` to make a note publishable, and never retry with other paths to get around a refusal. Never call the code of the plugin inside Obsidian (`obsidian eval`) to reach the publication center: confirmations are for the author alone. Report the message as it is.
4. **An error stops the run.** Report the text of the tool word for word and stop. A stale plan is the one exception: make the plan again, show it, and wait for a yes again.
5. **After a lost connection, read first, and treat a lock as a run that still goes.** When a call gets no answer (a reload of the plugin, a timeout), the run can go on without its answer. Wait, then run `status`. A lock error then means that the run still goes: wait and run `status` again. To know what a lost run did, ask the author to read the report of the publication center, or read the line `Plan: <id>` of the last commit of the copy.
6. **`unlock` only after a restart.** Offer it only when the author confirms that Obsidian and the command line program were restarted after the time of the lock, so that no run can hold it. The tool does not check it. A publication that stopped halfway is no case for `unlock`: the next `plan` puts the copy back.
7. **`confirm_store_state` only on an explicit yes of the author.** When a run stops because the state of the content store is not sealed (a commit that no tool wrote, or a store with no seal yet), show the difference of the message as it is and stop. Call `confirm_store_state` with the commit that the message names (`head`) only when the author read it and asked for the confirmation; never to get a plan through. A takedown still runs on such a state, and its deploy builds the last sealed state without the notes taken down, so the page leaves at once; the other changes go live only after the confirmation and a new deploy.
8. **Not on the real vault before the first publication.** Until the first publication to the preview host (issue 60 of the repository dsebastien-website) is done, run `publish`, `unpublish` and `takedown` only on a test vault (`bun run plugin:vault` in the repository). The tool also stops on a copy of the content store that has no `configuration.json`.

## Faces

| When                | Face                                                                                                                                                                                                                    |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Obsidian runs       | The MCP server of the plugin: `http://127.0.0.1:<port>/mcp` with the header `Authorization: Bearer <key>`. Settings of Vault Publish, "Copy the command"                                                                |
| Obsidian is closed  | `dsebastien-vault-publish mcp --vault <vault> --content-store <copy> --attachment-storage <folder>`, over the standard input and output. Add it with `claude mcp add vault-publish -- dsebastien-vault-publish mcp ...` |
| No MCP in the agent | The commands of the same names: `dsebastien-vault-publish status --vault <vault> --content-store <copy>`, and so on (`--help` gives every option)                                                                       |

The tools take the arguments of the commands: `plan` takes `include`, `hold`, `remove`, `pair` (a list of `{ "from", "to" }`) and `accept`; `publish` takes `plan` (the id); `unpublish` and `takedown` take `paths` (`unpublish` also `accept`); `deny`, `allow`, `ignore` and `unignore` take `path`. The places of the device are set one time: in the settings of the plugin, or as arguments of `mcp`. The deploy after a push needs five more settings of the device: the folder of the site code, the target file, the env file, the bun program and the time limit of a deploy (optional, 30 minutes by default) (in the settings of the plugin, or `--site-code`, `--deploy-target`, `--deploy-env-file`, `--bun` and `--deploy-timeout` of the commands and of `mcp`; `--no-deploy` skips the deploy). Ask the author for them; never guess a folder. Give the server the name `vault-publish` in both faces, so the tool names of this skill match. A call holds 1 MiB at most in the plugin: for a very large selection, use the command `plan --selection <file>`.

## Process

1. Run `status`. Read `counts`, `changed`, `new`, `movedEdited`, `pairings`, `toRemove`, `missing`, `tooLarge` and `behind`. A large result can come as a file: read `counts` first, then only the lists that you need.
2. When `behind` is above 0, stop and ask the author to pull the copy first (the Pull button of the publication center, or `git pull --ff-only origin main` in the copy).
3. Build the selection. By default a plan holds the `changed` notes only. Add to `include` the new notes that the author named, and the notes of `movedEdited` that the author confirmed (a moved note whose text changed can be another note at that path). Add to `hold` the changed notes that must wait.
4. Run `plan`. When `offline` is true, say that the plan uses the last fetch. When `listsNotRefreshed` is not empty, name those notes: their Dataview lists are published as they are in the note now, maybe not refreshed (the face of Obsidian refreshes them first; the command line program never does, and the log of the publication center gives the reason). When `liveQueries` is not empty, name those notes: their live Dataview or Bases blocks are not on the page. When `tooLarge` is not empty, name each note with its file and its size: the note links to a file above the size limit of an attachment (100 MiB), so the plan holds it; it is published or updated only when the file is smaller or the link is gone. Show the plan as rule 2 says.
5. Run `publish` with the id. Report `published`, `updated`, `removed`, `forcedRemoved`, `moved`, `failed` and `warnings`, and `originalsNotVerified`: the notes that also exist on the main site (articles, newsletters, news posts, and any note that the Ghost Publish plugin posted) whose post the tool could not verify, with the reason; they stay `noindex` until a publication verifies the post (the author fixes the property `public_ghost_blog_news_url` or `url` of the note, or the post). A result with `isError` and a report means that a note was left out: the text after the report names each such note with its reason. Give them to the author.
6. Read the deploy report. Over MCP, `publish`, `unpublish` and `takedown` answer right after the push: their last text is the object `deployment` with `state` `started`, and the deploy goes on in the background (about a minute). Call `deploy` with `last` set to true later: it starts no deploy, and gives `running` and the last report, the object `deployment` with `state` `done`. The commands of the command line program wait, and write the report in the text after the publication report, as its own object. A report has `push`, `takedown`, `build` and `deploy` (`ok`, `failed` or `skipped`), `live` with `url`, `uploaded`, `deleted`, `warnings` and `error`. Tell the author what is live. A failed build or deploy never undoes the publication and is no error of the tool: report its `error`, and run `deploy` again only when the author asks for it (`takedown: true` only for a takedown that the author named; a deploy runs with `--takedown` anyway while a takedown of this device waits for a deploy that succeeds). `takedown: true` in a failed report means that the notes taken down can still be live: tell the author. A deploy that names a missing setting deployed nothing: ask the author to set it. The output of the deploy is for the author only (the publication center, or `.git/vault-publish/deploy.log` of the copy for the command line program): never read it into the conversation.

## Guards

- `guards` reads the deny list (`denyList`), the open proposals (`proposals`) and the edits since the last publication (`edits`). It also works when a deny list entry names no folder.
- `deny` (a folder) and `ignore` (a note) apply at once when the new guard takes away no manifest entry (a published or an unpublished note) and, for `deny`, no attachment that a published note uses. Else the result has the state `proposed`, with the list `removes` (the entries that would leave the content store) or `affects` (the published notes that would lose an attachment). Tell the author that the proposal waits for a confirmation in the publication center.
- `allow` and `unignore` always give a proposal. Call them only when the author asked for that exact edit, and tell the author that it waits for a confirmation in the publication center. A confirmed `unignore` makes the note a candidate: it is published only when the author names it in `include`.
- A private folder that the author renamed stops every publication. Propose the fix: `deny` with the new path, then `allow` with the old path, which the author confirms.

## Unpublish and takedown

- `unpublish` removes the named published notes through a normal publication: their addresses answer 410, and a later publication can bring a note back with the same identity.
- `takedown` is for an emergency: the note leaves the content store at once, with no plan, and its addresses answer 404 after the next build. Name each path exactly as the manifest names it: the lists of `status` give the paths of the published notes, and `unpublished` the paths of the unpublished ones, also when their file is gone. Tell the author that copies in browser caches and at crawlers cannot be recalled, and that the text stays in the history of the content store. A takedown with `isError` means that the attachment storage gave a warning (it could not be listed, a file could not be deleted, or a file has a name that is not a key), so a file can still be public: report the files of `storageWarnings`. The files that macOS and Windows put into a folder (`.DS_Store`, `Thumbs.db` and `desktop.ini`, these exact names) stay with no warning, so a takedown with only such files left ends with success. The deploy that a takedown starts deletes the files of the takedown from the object storage of the host at once, also when its build fails; a failed deploy deletes no other file. A forced removal does the same, and the files that a guard withdrew from a held note leave the host at the next deploy. A deploy counts as a takedown when a takedown or a forced removal lies between the live release and the copy: it must be seen live. A deploy refuses a shallow copy of the content store: fetch its whole history.

## Messages

| The message says                                                                                                      | Do this                                                                                                                                                                                                      |
| --------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| The state of the content store is not sealed, or the seal key is missing                                              | Report the message word for word and stop. Confirm only on an explicit yes of the author (rule 7). A missing key is for the author to set                                                                    |
| The plan is stale                                                                                                     | Plan again, show the new plan, wait for a yes (rule 4)                                                                                                                                                       |
| A guard excludes a note, or a path is in no list                                                                      | Report it and stop. Never move the guard (rule 3)                                                                                                                                                            |
| The copy is locked                                                                                                    | A run still goes: wait and run `status` again (rule 5). `unlock` only as rule 6 says                                                                                                                         |
| A publication stopped halfway                                                                                         | Run `plan`: it puts the copy back. Then show the new plan (rule 2)                                                                                                                                           |
| A deny list entry names no folder of the vault                                                                        | Report it: the author renamed a private folder, and every run stops. Offer the fix of the section Guards                                                                                                     |
| `cannot be published: Obsidian reads its path as`, `has the same path in Obsidian`, or `Windows cannot hold its path` | Report it and stop. The author gives the file another name; never rename a note yourself. The warning of a move `whose path Obsidian reads as` or `a path that Windows cannot hold` stops nothing: report it |
| An edit has the state `proposed`                                                                                      | Tell the author that it waits for a confirmation in the publication center                                                                                                                                   |
| The settings miss a folder                                                                                            | Ask the author to set it in the settings of Vault Publish on this device                                                                                                                                     |
