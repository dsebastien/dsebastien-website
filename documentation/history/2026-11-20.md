## Issue 84 (gaps of the checks of the Markdown corpus)

### What was done

- One text reader for every check of `checkHtml()` (`packages/testing/src/markdown-forms.ts`): a space at each edge of a block element (`p`, `li`, `br`, headings, cells and the like), no text of a script or a style. A raw `LINK` line split over a paragraph and a list item is now found, and the code of a script no longer fails a check.
- A new check `hasText`: the text of the page holds a text, at least once or exactly `count` times. `embed-cycle` uses it, so a loop of embeds fails also when the HTML leaves out its end tags (the rewriter of Bun closes no element by itself).
- Of nested matches only the deepest counts, also without a text: `<div data-callout-fold="-"><details>` is one folded callout.
- `anchorsResolve` takes `target` and `nth`: in `headings-same-text`, the link `#Autumn#Tasks` must reach the second `Tasks` heading.
- `link-block` checks one line of each `LINK` form (a Markdown link, a note link with and without a label, the lists with a URL and with a note link, the `LINKS` lists, a block whose only target is on the deny list) and needs a link to the mulch and tools URLs. Its source pattern holds each of these lines (a mutation of each line fails the pattern).
- The runner of issue 26 ran again on the new corpus (merge and results on `prototype/markdown-adopt-check`): no score changed (14, 25, 8, 8, 12 of 47). Only the counts of the cells of `embed-cycle` and `link-block` changed; the research file says so.

### Decisions

- The author (R51): the three test seams, `hasText`, the deepest match also without a text, `target` and `nth` on `anchorsResolve`, and as a group the text reader, the `LINK` lines and the two links.
- A fact found on the way: the HTML rewriter of Bun keeps only the last end tag handler of an element, so the checker uses one handler per element and marks the matches of the selector in a handler before it.
