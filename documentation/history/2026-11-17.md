## Issue 64: export of the published corpus

- Built on the branch `ticket/64-published-corpus`, on top of issue 18, test first. The author asked for it: his published notes are better test data for size and speed than invented notes (decision R30).

Decisions of this ticket: R35 (readings of the agent, easy to change).

Review of issues 18 and 64:

- A review agent read both branches. It found no blocker and two major problems, both in the export. All that was real is corrected.
- The output folder of the two corpus commands had no check against the folders that a command reads. An output folder inside the vault got files, and an output folder that was the vault, with a file of the name of the marker in it, would have been emptied. The guard now resolves symbolic links, refuses a folder that touches the vault or the clone, accepts a marker by its content and not by its name, and refuses a path that is a file. Inside the clone, only the private folders that git ignores are accepted.
- The export followed symbolic links, so a link in the vault could bring a file from outside it into the export. It now copies a file only when its real path is inside the vault.
- The export checks its inputs before it removes its earlier output, counts a file one time, and goes on after a file that it cannot read.
- The corpus did not have the size of the public notes (15 MB for 71 MB) and half of their links. The text length and the number of links are now tuned to the totals of the research, and a test checks both. A link to a heading no longer names a heading that a stub does not have.
- The images of the corpus are written without a compression library, so their bytes cannot change with a library version. A test pins the digest of a small corpus.
- The one real export that ran before these corrections used the default output folder, which was safe.
