## Issue 37: renames, the third review

Branch `ticket/37-renames`. Decision R66, ADR 0012. The work and the first two rounds of the review are in `2026-11-22.md`.

### Review

Round 3 (a separate reviewer on the whole ticket, from new angles: the life of a note over many runs, two devices, Windows, size, the faces, the fixture site with curl). One blocker, corrected in both implementations with a shared scenario first:

1. A vault that was behind on one device (its journal had fewer lines than the count of the content store) lowered the count, so the lines came back when the vault caught up, and an old move could move a new note at the same path and publish a note that the author never selected. A journal with fewer lines than its count now applies nothing, keeps its count, and gives a warning.

Also corrected:

2. A name that a note had only while it was unpublished became a public former path when the note was published again. An unpublished entry now takes only the guard rule of the moves and does not move: its old address stays gone (410), and its new path never becomes public.
3. The errors of the TypeScript reader of the journals name the folder and the journal, as in Rust. The help of `status`, `plan` and `publish` names the moves and the pairings, and the message of a stale plan names a rename journal.
4. `Configuration.md` says that git must not convert the line ends of the journals (the read marker hashes their bytes; this vault has `eol=lf`).

Checked by the reviewer and found right: a refused push puts `renames.json` back and the lines are read again; another device that publishes first; a rename during a publication waits for the next run; a journal of 100,000 lines (`status` 0.55 s in TypeScript, 1.6 s in the Rust debug build); a folder rename of 2,000 notes (3.3 s to publish); the old address of the moved note of `site:fixture` and its variants, with no chain.

Not changed, in GitHub issue 105 (the follow-ups): a takedown or an unpublish that names the new path of a move that is not published yet is refused with no hint of the old path; the rule of round 2 compares the time of a line with the first publication, which come from two clocks; a move to a name that Windows refuses (`:`, `?`) can stop every publication on a Windows device; the former paths make the resolver map larger and are never removed, and `scripts/measure-resolver-map.ts` does not count them; a former path that two notes held at different times gives the "not found" page with both.

One look at the commit of the corrections of round 3 (a separate reviewer): no guard opens, and the two implementations agree on seven probes. Its points are GitHub issue 105 (the rule of the author: a later finding is an issue unless it opens a guard). The largest: an unpublished entry still leaves its path during the fold, so a published note that moves into that path does not move, and its text shows as a candidate under the unpublished entry; only an include of the author publishes it.

### Verified

- The reviewers asked the fixture site with curl: the old address of the moved invented note, its variants, HEAD, `Accept: text/markdown`, the old Markdown path; one hop, no chain.

## Issue 39: the publication center

Branch `ticket/39-publication-center`. Decision R67.

### Decisions of the author

1. Issue 105 point 1 is fixed first, in this ticket, with a new rule: a published note that moves into the path that an unpublished note left takes it, and the unpublished entry leaves the manifest (rule 6 of the moves). The fix that issue 105 proposed (the unpublished entry keeps its path in the fold) gave the same result as before: the published note did not move, and its text showed as a candidate under the entry of the unpublished note.
2. The settings of a device (the copy of the content store, the attachment storage, the git program) are in a settings tab, kept in the local storage of Obsidian.
3. The view works as Obsidian Publish does: the lists show what happens, the author ticks, and one click publishes. The label of the button states the plan, from the function that makes every plan; a publication whose plan differs publishes nothing.
4. An unpublish is a mark that the next publication applies. A takedown has a dialog with the note, what goes and what stays, and one button.
5. A pairing is not confirmed by default.
6. The status bar shows the state at the last check, with a mark after an edit.
7. A check runs when the view opens, on Refresh, on the command and after each run, never at the start of Obsidian.
8. A Pull button when the copy is behind.
9. The plugin records the measures of the budgets by hand; their values are a later decision.

### Done

- The logic: `planLists()` of `plan.ts` (the lists of a plan from the queue, used by `computePlan`), and the model of the view, `publishing/center.ts`.
- The fix of issue 105 point 1 in both implementations, with a shared queue scenario.
- The plugin: the settings tab, the controller (`app/center.ts`), the view (`app/view.ts`), the status bar item, six commands, the measures (`app/measures.ts`), `styles.css`.
- `pullContentStore()` and the option `git` of `nodeDevice()`.
- `SITE_ORIGIN` of `packages/resolver`, which the build and the plugin read.
- `bun run plugin:vault [--corpus]`: a test vault for the check by hand.
- The checklist of PERF-17 in `documentation/Configuration.md`.

### Decisions of the author during the reviews

10. A moved note whose text at its new path is not the published text is in the new queue list `movedEdited`, and its update waits for a tick (the tool cannot tell an edit after the rename from another note at that path). The publication of the move writes `updateHeld` into the manifest entry, so the hold lasts until a selection includes the note.
11. Every run stops when the copy has no `origin` or its last commit has no `configuration.json`: a wrong folder in the settings must never read as a content store with an empty deny list.

### Review

Round 1 (the whole diff): 1 blocker, 6 major, 9 minor. The blocker: a takedown of a moved note at its new path took down another entry. Also corrected: an unpublished note whose move the vault did not show yet gave its path away; a move onto another note at the new path made that note a ticked update (on main before this ticket); the pull and the fetch did not take the lock; no way out of a crash in the plugin (now a command removes the lock); a takedown refused without a message during a check; choices lost during a run; the edits counted from the start of Obsidian and one render per edit.

Round 2 (the corrections): 3 blockers, 4 major, 6 minor. A draft at the old path, a partial synchronization and a swap with an edit could publish a text that the author never ticked (now `movedEdited`, decision 10); a takedown after a publication used an old queue; the stop for a changed new note was one click deep.

Round 3 (new angles: many runs on two devices, 870 random scenarios on both implementations with no difference, the user on a new device, the keyboard, names with right-to-left marks): 1 blocker, 7 major, 5 minor. The blocker: the hold of a moved note lasted one publication only (now `updateHeld`). Also corrected: a copy with no configuration or no origin (decision 11); a tick and an unpublish mark of one note; a ticked moved note that changed after the check; the pull after a crash after the push; a takedown after a rename with no check; the focus of the keyboard; isolated names; truer messages.

Not corrected, in the follow-up issue: a note that goes back to a path where it has an unpublished entry loses its redirect; the write of `public_note` goes through Node and not through the API of Obsidian; the short window that takes the writes of a run for no edits; a lock whose process is dead; a new activity clears the error of the last one; the Check button of the settings can show an older error; error texts do not isolate names; a crash scenario for a displaced entry.

The last look at the commits of the corrections of round 3 (a separate reviewer) opened no guard. It found that the check before a takedown could stop it (PUB-99), corrected: a check that fails leaves the last check, and a takedown stops only when the note moved since its dialog. Its other points are GitHub issue 106.

## Issue 41: the MCP server and the skill of the tool

Branch `ticket/41-mcp-server`. Decision R68.

### Decisions of the author

1. The plugin hosts the MCP server itself, as the Starter Kit plugin does: a Node HTTP server on 127.0.0.1 with one endpoint `/mcp`. The server of the Starter Kit and the REST and MCP server plugin are not used, so the third fact of K15 no longer matters.
2. The server is on when the plugin loads, and a key is always required. The first start makes the key and keeps it in the secret storage of Obsidian on that device.
3. The skill is in the repository (`skills/developassion-publish-notes/SKILL.md`), and a copy is in the vault now.
4. After review round 1, the author did not mind whether an agent call that publishes a new note, pairs, unpublishes, takes down or unlocks needs a confirmation in Obsidian. The reading of the assistant: no dialog, and the skill allows only `status` ahead of time.
5. The release process of the Obsidian Starter Kit (in the vault) now says that the plugin, its MCP server, the skill and the command line program are for the vault of the author only.

### Done

- The Rust command `mcp`: the tools over the standard input and output, one message of JSON per line, a new device for each call.
- `apps/plugin/src/publishing/mcp.ts` and `cli/src/mcp.rs`: the messages (initialize, ping, tools/list, tools/call), written by hand in both faces. The tools are one file that both read (`mcp-tools.json`). The shared cases of the messages are in `fixtures/canonical/mcp.json`.
- `apps/plugin/src/app/mcp-server.ts`: the HTTP server of the plugin, with the checks of the key, the `Origin`, the `Host`, the type and the size of a body, and the version of the protocol.
- `PublicationCenter.serve`: each call of the plugin goes through the controller of the view. The check after a run now runs inside the activity of the run, for the view and for the agents.
- The settings tab: the server on or off, the port, the key (copy, make a new one), the command for Claude Code.
- The skill `developassion-publish-notes`, and a narrow exception for it in the check of private files.

### Review

Round 1 (the whole diff): no blocker, 3 major, 13 minor. Corrected: the Rust `mcp` kept one device for the whole session, so a note written during the session was not seen (now a new device for each call); the check after an agent call was refused when a second call waited (now the check runs inside the activity of the run, for the view and for the agents); a check after an agent run cleared the marks of edited notes; an action of the author was refused while an agent read; a notice for each agent read; a line that is not UTF-8 ended the Rust server; ids that the two faces read in another way; `plan` marked as read only; the key in a `.mcp.json` (now `--scope local`); docs. Finding 3 (no person confirms a call that changes the site) went to the author: decision 4 above.

Round 2 (the corrections): no blocker, 1 major, 7 minor. The major point: the notice at the end of a run showed the check after it, so the author would not see that an agent published (now the state keeps the `outcome` of the run). Also corrected: the marks of every new note and moved note whose text changed are kept after an agent run; an agent read leaves the error of the author; a body that is not UTF-8 and a number that a double cannot hold get a parse error in the plugin too; a test that passed on the old code.

Round 3 (new angles: a real client session on both faces, the two faces on one vault, a client that disconnects, a reload, thousands of paths, the skill read cold): no blocker, 2 major, 8 minor. Corrected: Claude Code cuts the middle of a long error result, so the failure text now names each note that was left out with its reason (both faces, also on the error output of the commands); after a reload, the skill led an agent to offer `unlock` while a run of the old load went on; the Host `localhost` could send the key to a program on `[::1]` (now only `127.0.0.1`); the exception of the private files check accepts only the skills of this repository by name; docs of the limits.

The last look at the corrections of round 3 (a separate reviewer) opened no guard. Its four points are in GitHub issue 107, with the points that the rounds left for later.
