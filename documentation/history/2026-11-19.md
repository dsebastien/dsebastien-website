## Issue 35 (attachments)

Done in both implementations, with tests first at the five seams that the author approved: shared cases, queue scenarios, the publication on the fixture vault, parity, and the note page through the build and the plain server.

### Decisions of the author (R45)

- Every kind of file that a published note links to can be an attachment, also a canvas or a base. The assistant proposed the media kinds only, because a canvas holds the paths of the notes on it, also of private notes. The author chose every file.
- The tool reads the width and the height of an image and writes them into the manifest entry, so the build reads no image. A changed image has a new hash, so each note that uses it is a technical update, and the publication writes the new size.
- After each publication that passed its checks, the tool deletes every file of the attachment storage that no published note lists. It lists the names only, and reads no file.

### What the tool does now

- A link leads to a file that is not a note first, as in Obsidian: `[[plan.png]]` leads to `plan.png`, also when a note `plan.png.md` exists. The scan lists every file of the vault, and the files of the deny list folders by their paths.
- Each link of a note to such a file is an item of the list `attachments` of its manifest entry: `hash`, `link`, `path`, `size`, and `width` and `height` of an image. A file of a deny list folder is never one (GATE-42), and a file whose name ends in `.md` in another letter case is never one, because it would pass the ignore guard.
- The size of an image comes from its first bytes: PNG, GIF, WebP (VP8, VP8L, VP8X) and JPEG, with the rotation flag of a photo, so a turned photo is not stretched. A new shared file, `fixtures/canonical/images.json`, holds 38 cases.
- The publication uploads each new attachment before the files of its note, as a part of the unit of the note. A failed upload leaves the note out. After a refused push, the uploads of the run that no published note lists are deleted. After each publication, the files that no published note uses leave the storage. The report has two new lists, `attachmentsUploaded` and `attachmentsDeleted`.
- The cleaning step is version 3: every published note becomes a technical update at the next publication.
- The command line program takes `publish --attachment-storage <folder>`. The storage is a folder for now: the object storage and its credential come with the hosting (OPEN-12).
- The site: an attachment has the hashed URL `/-/attachments/<key>/<name>`, and the resolver map gives the key of each one. An embed of an image is an image with its width and its height, lazy loaded. A video and a sound get the player of the browser. Every other link to a file is a link. An embed of a file under a guard stays plain text. The plain server (`bun run serve --attachments <folder>`) gives the files with a cache time of a year, no right to run a script, and range requests (206 and 416).

## Issue 36 (failure cases, the lock and the device opt-in)

Done in both implementations, with tests first at the four seams that the author approved: shared scenarios with new steps (`crash`, `unlock`, `offline`, `online`, `lose`), a push refused because another copy pushed first on the fixture vault, parity of a crash of each implementation that the other one puts back, and the write of a note in one rename.

### Decisions of the author (R46)

- No device opt-in. Story 96 and TOOL-11 are dropped: the author is the only publisher. The case of a vault that lags behind on one device, whose older texts look changed, is the new GitHub issue 74.
- The lock of the device is a file of the copy, made in one create by `publish`. `status` and `plan` stop while it is there. A lock that a crash left is removed only by the new `unlock` command.
- Without a network, `plan` uses the last fetch and says `offline: true`; `publish` stops. This changes the reading R44 that `plan` stops too.
- After a refused push, the author pulls by hand (`git pull --ff-only`), as in R44.
- A publication that stops halfway leaves a run journal. The next `plan` or `publish` puts the copy back, takes back a commit that did not arrive, and owes the correction of `public_note` when the push arrived. The tool never pushes an old commit (PUB-94 is changed so).
- Each publication uploads again every file that a published note uses and that the attachment storage lost, when the vault still has its bytes.
- Six small rules, accepted as a group: the queue list `missing`, `plan` takes the lock while it puts the copy back, `status` stops on a journal whose run may not have pushed, the correction owed after a crash after the push, the write of a note into a hidden file and then a rename (a read-only note is refused), and the list `failed` sorted by path.

### What the tool does now

- `status` gives a list `missing`: the published notes whose file this device does not have and that no guard excludes. A plan never takes them by default. The forced removals of a plan are now `toRemove` without `missing`, in both implementations.
- `publish` takes the lock (`.git/vault-publish/lock`: the command, the device, the face, the time, the process) and removes it at its end. `status`, `plan` and `publish` stop while it is there, with its content and the way out (`unlock --content-store <folder>`).
- Before its first write into the copy, `publish` writes the run journal (`.git/vault-publish/journal.json`): the commit before the run, every path of the store that the plan can write, the plan, and whether a correction is owed. After the push, the journal says `correct` until the correction of the property and the cleanup are done. A failure that the undo fully took back removes the journal; a failure that left a file or a commit keeps it, so the next run puts it back.
- The next `plan` or `publish` reads the journal: with no commit of the run, each path gets the bytes of the commit before the run; with a commit of the run, it fetches and either keeps it (the push arrived: the correction is owed) or takes it back. Without a network, the tool stops in that case. `status` writes nothing, so it stops on such a journal.
- `plan` without a network uses the last fetch and says `offline: true` (and the program warns on its error output); a copy that was behind at the last fetch still stops it. `publish` without a network stops.
- After the cleanup of the storage, every key that a published entry uses and that the storage does not have is uploaded again from the vault, when a file of the vault has those bytes, with a warning. Else a warning says that the note shows the file as missing until its next update.
- A write into a note goes to `.<name>.vault-publish` in its folder, then a rename. A read-only note is refused, as before.
- The list `failed` of the report is sorted by path.
- The Rust program has a crash switch in its debug build only (`DSEBASTIEN_VAULT_PUBLISH_TEST_CRASH=write|commit|push`). The TypeScript tests use `crashingStore()` of `packages/testing`.
