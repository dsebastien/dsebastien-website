# 2026-11-19

## Issue 35 (attachments)

Done in both implementations, with tests first at the five seams that the author approved: shared cases, queue scenarios, the publication on the fixture vault, parity, and the note page through the build and the plain server.

### Decisions of the author (R45)

- Every kind of file that a published note links to can be an attachment, also a canvas or a base. The assistant proposed the media kinds only, because a canvas holds the paths of the notes on it, also of private notes. The author chose every file.
- The tool reads the width and the height of an image and writes them into the manifest entry, so the build reads no image. A changed image has a new hash, so each note that uses it is a technical update, and the publication writes the new size.
- After each publication that passed its checks, the tool deletes every file of the attachment storage that no published note lists. It lists the names only, and reads no file.

### What the tool does now

- A link leads to a file that is not a note first, as in Obsidian: `[[plan.png]]` leads to `plan.png`, also when a note `plan.png.md` exists. The scan lists every file of the vault, and the files of the deny list folders by their paths.
- Each link of a note to such a file is an item of the list `attachments` of its manifest entry: `hash`, `link`, `path`, `size`, and `width` and `height` of an image. A file of a deny list folder is never one (GATE-42), and a file whose name ends in `.md` in another letter case is never one, because it would pass the ignore guard.
- The size of an image comes from its first bytes: PNG, GIF, WebP (VP8, VP8L, VP8X) and JPEG, with the rotation flag of a photo, so a turned photo is not stretched. A new shared file, `fixtures/canonical/images.json`, holds 38 cases.
- The publication uploads each new attachment before the files of its note, as a part of the unit of the note. A failed upload leaves the note out. After a refused push, the uploads of the run that no published note lists are deleted. After each publication, the files that no published note uses leave the storage. The report has two new lists, `attachmentsUploaded` and `attachmentsDeleted`.
- The cleaning step is version 3: every published note becomes a technical update at the next publication.
- The command line program takes `publish --attachment-storage <folder>`. The storage is a folder for now: the object storage and its credential come with the hosting (OPEN-12).
- The site: an attachment has the hashed URL `/-/attachments/<key>/<name>`, and the resolver map gives the key of each one. An embed of an image is an image with its width and its height, lazy loaded. A video and a sound get the player of the browser. Every other link to a file is a link. An embed of a file under a guard stays plain text. The plain server (`bun run serve --attachments <folder>`) gives the files with a cache time of a year, no right to run a script, and range requests (206 and 416).

### Acceptance of the issue

1. A published note with an image shows the image with its width and its height: the note page test (`apps/site/src/attachments-page.spec.ts`).
2. Only the attachments that published notes use are in the storage: the queue scenario "the attachments of a note" and the publication tests, in both implementations.
3. An attachment in a deny list folder is never uploaded: the publication tests and the page test, in both implementations.
4. After a failed push, the storage holds no file that the manifest does not list: the publication tests with a refused push, in both implementations.
5. A request for a part of a large media file gets that part only: the page test, with a video of 3 MiB that the test makes.

- A file that came under a guard stayed in the storage when the plan held its note or its update failed: the old entry still listed it. The author decided (R45) that such a file leaves the storage at the next publication, with the name rule of the forced removal of notes. Corrected with a new shared scenario.

- A PDF with the `sandbox` policy may not show in a browser. The plain server no longer sets it on a PDF.
- Recorded as issues: 72 (a file above 2 GiB stops the plugin under Node, and every run reads every attachment) and 73 (the two implementations make small letters from different versions of Unicode). Comments on issues 21 (the cleanup runs before the deploy, and the headers to check in a browser), 36 (two devices at the same time, a file missing from the storage, the order of `failed`) and 45 (an image inside a link).

### Second review

A second review agent read the commit of the corrections (`093a252`). It found two more ways for a file under a guard to stay in the storage, both reproduced in both implementations, and corrected with a shared scenario that failed first:

- The file moves into a deny list folder, and another file takes its old path. The scan then found a file at the path, so the old key stayed. Now an attachment whose path holds other bytes counts for no note when a file of its name is in a deny list folder.
- The file moves into a hidden folder of a deny list folder (`Locked/.stash/`). The scan skipped hidden names, so its name was not known. Now the names below a hidden name of a deny list folder count for the name rule, for attachments and for notes (the same gap existed for a published note). They are still no candidates of a link.

Also corrected: a public file with the name of a file of a deny list folder keeps its key (a test now says it), the Rust test of a takedown with no storage now runs on Windows too (the program no longer refuses a missing storage folder before the run: a note whose upload fails is left out), the text of the canonical form for `.<key>.part`, and the PDF exception in R45. These corrections had no review of their own: the author allows two rounds per ticket, and they close the findings of the second one. Each new branch was checked with a mutation in both implementations.
