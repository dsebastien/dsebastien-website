## Second session of the day: issue 33 (publication queue)

### Done

- Issue 33: the publication queue, the selection and the plan, in both implementations.
    - `status` gives the four lists with counts: new, changed, to remove, unchanged. The technical updates are a part of the changed notes.
    - `plan` takes paths to include, to hold and to remove. A plan without paths holds the changed notes only. A new candidate enters a plan only when its path is named.
    - `publish` publishes new notes, updates and removals in one commit, and writes the publication report: published, updated, removed, skipped, failed, warnings, and the notes whose property was set or removed.
    - The `public_note` property is corrected after the push, on the notes of the scan only. A note that carries it by mistake is not published and loses it.
    - The record of a plan holds the hash of each cleaned note, and the publication writes exactly that text. A stale plan is refused, also when another published note changed after a plan without paths.
- The canonical form has new sections, written before the Rust code: the notes of the vault, the publication queue, the selection, a publication, the publication report, the state property after a publication, and the strict reading of the manifest.
- New shared file `fixtures/canonical/queue.json`: three scenarios on small invented vaults, with the queue, the plans, the reports and the files that each step must give. Both test suites run it. `fixtures/canonical/properties.json` has cases for the removal of the property.
- The parity test goes through a story of the queue (first publication, edits, a technical update, a removal, a held note, a note with the property by mistake) and compares the queue, the plans, the reports, the content store and the vault.

### Defects that the work showed

- The first slice broke PUB-14 for a note without properties: after the tool added the properties to write `public_note`, the source of the note was another text, so the note would count as changed after its own publication. The source of a note now leaves out properties that hold no line.
- A refused push removed the files of the publication from the copy. For an update that removes a file of the last commit. The files are now put back as they are in the last commit.
- A note name with `[`, `*` or `?` was a pattern for git, so a commit could take a file of another name. Every git command of the tool now reads paths as they are written.
- The parity test caught a TypeScript sort with the default order of texts in the record of a plan.

### Review of the ticket

A review agent read the diff and found one blocker and three major defects. All are corrected in both implementations, with tests.

- Blocker: the correction of the property could open the ignore guard. On a published note with the ignore property in properties that are never closed, or below the state property, the write of `public_note` changed what the guard read, and the next plan without paths would publish the note. A write now never changes what the ignore property says: the note is left as it is, with a warning. A shared scenario holds the two forms.
- A commit that failed (a hook, no identity) left the files of the publication in the copy, and the next run read them as published. A failed commit is now taken back like a refused push. A copy with no commit works.
- A large publication gave every path to git as an argument and passed the limit of the system (issue 66). The paths now go to git in a file. Checked by hand under the default limit of Linux: 10,000 notes with long paths, in both implementations.
- The removal of the last property could turn a text of the author into properties, and one form of empty properties made a note changed after its own publication. The two lines of empty properties now stay when the text below them would be read as properties, and the source drops them one time only.
- The two readers of JSON did not accept the same files (a version written as `1.0`, half of a surrogate pair, a number too large), a symbolic link in the manifest was a file for Rust only, and the check of the device name differed. Each has one rule now.
