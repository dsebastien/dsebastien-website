## Third session of the day: issue 34 (guards and link resolution)

A guard excludes a published note in three cases: it has the ignore property, its folder is on the deny list, or it was moved into a deny list folder. The tool knows a move by the file name: it lists the names of the deny list folders and reads none of their files. The author decided that rule in the session. ### Sixth review of issue 68, the last round

A review agent read commit `18ebc66`. The hash check does well: a deleted, untracked, ignored, linked, case-changed or empty file stops the tool. It found two ways to open a guard, both in the advice for commits that the content store does not have, both reproduced with the release program:

- A commit that removes `configuration.json` names only that file, so the message proposed to push it. The reviewer followed the advice, and the next `status` listed a note of a deny list folder as new.
- A merge commit names no file in `git log`. A merge that keeps the files of the copy (`git merge -s ours origin/main`) takes back what another device pushed, for example the forced removal of a note under a guard, and the message proposed to push it.

Both are corrected, with tests that failed first in both implementations. The advice now reads what a push would change: `git diff --no-renames --name-status origin/main HEAD`, or every file of the last commit when the content store has no branch yet. It proposes the push only when the push changes `configuration.json` alone and does not remove it, or changes nothing.

A third point could hide a published note too, with an attribute that the author sets by hand: a filter (or `working-tree-encoding`) of git made other bytes look like the commit, for git status and for `git hash-object`. The tool now hashes the bytes that it reads with `--no-filters`, and a test with a clean filter that puts a deny list entry back shows that the run stops. The same change corrects a false stop: a configuration committed with Windows line ends in a copy with `core.autocrlf=true` stopped the tool, and no advice helped. A file is now the file of its commit when its bytes, or its bytes with each carriage return and line feed made a line feed, have the hash of the commit.

The file lists of the message are now the same in both implementations (sorted by path), and a merge that changes nothing gives no empty list.

Not corrected, they stop the tool and do not open a guard (GitHub issue 71): the advice for a configuration that git assumes unchanged and that was edited (it proposes a commit, which stages nothing), the advice for a configuration replaced by a symbolic link (it proposes to commit the link), and the advice for a configuration that was added and then removed from the disk before a first commit.
