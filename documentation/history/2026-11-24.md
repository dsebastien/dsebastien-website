## Issue 42: rules for agents and edits of the guards

Branch `ticket/42-agent-rules`, started on 2026-11-23. Decision R69. The rules are in `Canonical Form.md`, section "The edits of the guards".

### Decisions of the author

1. An edit that makes the guards looser (`allow`, `unignore`) is always a proposal, from the command line program and the MCP server. Only the author confirms it, in the publication center. The "names it in the request" path of GATE-40 is dropped: the tool cannot check it.
2. An edit that makes them stricter (`deny`, `ignore`) applies alone only when it takes no manifest entry away. Else it is a proposal that names the entries that would leave (`removes`).
3. The proposals and the log are `edits.json` in the content store: one commit and a push for each edit.
4. After review round 2: a `deny` that puts under the guard an attachment that a published note uses is a proposal too, and it names those notes (`affects`).
5. After the last look: a publication from an agent face stops when its plan has a forced removal, or a published note that would lose a file under a guard (`guardedAttachments`), that the request does not name (`accept`). The view never stops. This replaces a check of each edit that applied alone (rule 10).

### Done

- `edits.json`: a strict reader, the event id, the canonical write, the open proposals and the events since the last publication, in both implementations (`apps/plugin/src/publishing/edits.ts`, `cli/src/edits.rs`).
- The queue has `proposals`, and the plan has `edits`: a new event makes a stored plan stale. A publication raises `published`, so that the next plan shows only the newer events. `edits.json` is one of the files of the copy that must be the files of its last commit.
- The commands `guards`, `deny`, `allow`, `ignore` and `unignore` in the Rust program, and the same tools in both MCP servers. The edits take the lock (`edit`), fetch, use the run journal, and push. In TypeScript: `guards`, `edit`, and for the view only `reviewProposal`, `confirmProposal` and `rejectProposal`.
- `removes` and `affects` come from two sets of guards on one read of the vault, of the journals and of the manifest.
- The selection list `accept` and the plan list `guardedAttachments`: a `publish` or an `unpublish` from an agent face stops when a forced removal or a note of `guardedAttachments` is not in `accept`, and every cleanup of the attachment storage of an agent run keeps the guarded files of published notes that `accept` does not name (rule 10).
- The publication center: a section of the open proposals, with Confirm and Reject, and a dialog for each confirmation, which shows the lists in full; the dialog of an `allow` names the published notes whose next update would upload a file of the folder (rule 11). The plan part shows the edits since the last publication.
- The skill `developassion-publish-notes`: the guards, the proposals, `affects`, the edits of a plan, and the rule that an agent never writes the files of the guards itself.
- Shared scenarios in `fixtures/canonical/queue.json` and `fixtures/canonical/mcp.json`, and `parity/edits.spec.ts`.

Also corrected: one read for both scans; the dialog showed only the first lines; a wrong text in the dialog of an `allow`; help texts. Point 8 went to the author: decision 4 above.

Round 3 (new angles: about 600 random cases of edits and publications on both implementations, the rule checked from end to end, two devices, a real MCP session, the skill read cold, a vault of 3,000 notes): 1 blocker, 2 major, 2 minor. The blocker: an edit that applied alone on one device could take a published note away on another device, whose rename journal had moved that note into the folder (now rule 10). A look at that change found one more blocker, corrected: a stale plan of an agent cleaned the attachment storage before the check of `accept`, and deleted the guarded files of published notes. Its two minor points: the refusals of a bad path of `accept` (corrected), and a note listed in `guardedAttachments` that loses nothing (issue 108).

## Issue 40: frozen lists (decision R71)

Branch `ticket/40-frozen-lists`. The rules are in `Canonical Form.md`, section "The frozen lists of a note".

### Decisions of the author

1. The Dataview Serializer gets a public API `refreshNotes(paths)` that reports one outcome per note (DEP-02). No dry mode: the refresh writes before the plan.
2. In Obsidian, Dry run, Publish and the `plan` tool of the MCP server of the plugin first refresh the lists of the notes of the plan, then compute the plan. PUB-33 and PUB-92 get one exception each: the refresh writes only the output of the serializer, and Publish can publish lists newer than the ones of a dry run.

### Done

- `frozen.ts` and `cli/src/frozen.rs`: a note has a live query (a fence `dataview`, `dataviewjs`, `base`, `bases` or `query`) and a list to refresh (an automatic marker of the serializer outside a fence). 49 shared cases in `fixtures/canonical/frozen.json`, with the known limits of rule 9.
- The `plan` command of both implementations gives `listsNotRefreshed` and `liveQueries`, outside the record. The Rust program refreshes nothing (PUB-101) and says so on the error output. A publication warns for each published or updated note with a live query (REN-14).
- The port `ListRefresh` and its face `app/serializer.ts`: the plugin asks only the notes of the plan with a list to refresh, reads the answer strictly (a note counts as refreshed only when the serializer updated it or found it up to date, for that exact file, with no error and no skipped query), does not ask a path that Obsidian changes (issue 110), waits at most 10 minutes, and computes the plan again when a note changed during the refresh.
- The publication center: the events of a refresh wait for its end; one event per write of the refresh (`writes`) is its write, every other event is an edit, so a new note that another program edits during the refresh is still refused. The dry run panel and the run log name the notes that the refresh changed, the notes whose lists were not refreshed with the reason, and the notes with a live query.
- The Dataview Serializer, branch `feat/refresh-notes-api`: `refreshNotes` with five states, eight outcomes, `writes`, `resolvedPath`, `stalePaths` and `unsettledPaths`; a check of the index of Dataview against the disk with a wait; up to three passes for notes that depend on each other; a per-note lock; an all-or-nothing write. Its reviews also corrected older bugs of the serializer: a marker line with trailing spaces, CRLF notes, multi-line definitions, an empty result in a callout.
- The skill `developassion-publish-notes`, `mcp-tools.json`, `Configuration.md`, PUB-33, PUB-92, PUB-101 and DEP-02.

Round 1 (the whole diff): website 0 blocker, 2 major, 11 minor; serializer 1 blocker, 4 major, 6 minor. The website points: an edit of a new note during the refresh was hidden from the check "a new note changed after the check" (now each event counts), and PUB-92 was false for Publish. ## Issue 110: paths that Obsidian changes (decision R72)

Branch `ticket/110-obsidian-paths`. The rules are in `Canonical Form.md`, section "Paths", rule 4.

### Decisions of the author

1. Both implementations refuse a note whose vault path Obsidian changes, with a message that tells the author to rename the file (option 2 of the issue, not a map of the paths). The author renamed the one such file of the vault now ("Ten Personal Knowledge Management Practices to Explore and Master (Article)": a no-break space became a space), so its URL is the URL of Obsidian Publish, and the ten links to it resolve.
2. The rule covers every change of `normalizePath`: U+00A0, U+202F, a backslash, a slash too many, a name that is not in NFC. A name in the decomposed form is no longer published as the disk writes it (R47 changes for that case).

### Done

- `obsidianPath`, `isChangedByObsidian` and `obsidianTwins` in `names.ts` and `names.rs`, with the shared cases `obsidian` and `twins` (the behavior of `normalizePath` was read from the bundle of Obsidian 1.15.1).
- A plan stops when a note of `publish` or the `to` of a pairing has a path that Obsidian changes, or a twin (another note of the scan with the same Obsidian path). A plan without a new note and without a pairing never stops on it.
- The Starter Kit is never asked about such a path or about a published note with a twin (`askable`, the published question). The plugin does not refresh the lists of such a note.
- A line of a rename journal (`note` or `folder`) does not move an entry to such a path: a warning, and the note shows as a pairing.
- The scenario of issue 73 publishes U+01F0 in place of `j` and U+030C, and keeps its point.
- Three shared scenarios in `fixtures/canonical/queue.json`, the documents (`Canonical Form.md`, PUB-102, R72, the glossary, the skill).

### Review

Light review (R73, decided in this session): one round of two reviewers, then one look at the corrections.

Round 1: documents and consistency (Sonnet), 0 major, 5 minor (comments, the glossary, the skill), all corrected. Break it: 0 blocker, 1 major, 3 minor. The major point: two files with one Obsidian path (`X Y.md` and `X` U+00A0 `Y.md`); the plain one was still published, and Obsidian could answer for the other. Corrected with the twins. Also corrected: no scenario of a `folder` line. The click of the view on such a note is issue 114. A journal line whose path holds a backslash is not a valid line and moves nothing (documented).

The last look at the corrections: 0 blocker, 0 major, 8 minor. The documents that said a twin is never published, or that a published entry at such a path comes only from an old store, are corrected (a published note that gets an Obsidian twin later stays published, with no type). The glossary term is "Obsidian twin", because "twin" already names a translated note in the spec. The code points are issue 115.
