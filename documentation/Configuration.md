# Configuration

## TypeScript

`tsconfig.json` at the repository root. Maximum strictness, from the Obsidian plugin template of the author, plus `exactOptionalPropertyTypes`, `useUnknownInCatchVariables`, `noUncheckedSideEffectImports` and `forceConsistentCasingInFileNames`.

- `types` is pinned to `bun` and `node`, so that a missing type package is a hard error.
- `allowJs` is off: JavaScript files cannot skip the type check.
- `lib` includes `DOM` for now. Packages that run only on a server get their own configuration without it.
- `jsx` is not set. It is added with the first package that needs it.
- Packages and apps extend this file. An Astro app also extends the strictest Astro preset.
- The root project holds `scripts/`, `packages/`, `parity/`, `apps/plugin/` and the configuration files: `bun run tsc` checks them. The site has its own `tsconfig.json` and is not part of the root project: `bun run check` runs `astro check` on it, where a warning fails the run.
- In `apps/site/tsconfig.json` the root configuration comes after the Astro preset, so that the strictness of the root wins (`allowJs` stays off).

## Workspaces

The root `package.json` declares the Bun workspaces `apps/*` and `packages/*`. `apps/site` is the Astro site. `apps/plugin` is the Obsidian plugin. `packages/testing` is the test support (`@dsebastien-website/testing`): it has no build step, and its entry is its TypeScript source. The root package depends on it, so that the tests of the root (`parity/`, `scripts/`) can import it. The root `Cargo.toml` declares the Cargo workspace, with `cli` as its only member.

## Lint

ESLint (`eslint.config.ts`): the recommended rules of ESLint, the strict rules of typescript-eslint with type information, and the recommended rules of `eslint-plugin-astro` for Astro components. Every rule is an error, and the lint script adds `--max-warnings 0`. `eslint-config-prettier` switches off the rules that Prettier owns.

Rust: `cargo clippy` with every warning denied. The Cargo workspace denies the `all` and `pedantic` groups of clippy and forbids unsafe code. `rust-toolchain.toml` pins one exact version of the toolchain for the machines of the author and for CI (the workflow names the same version, and a guard test compares the two): with "stable", a new version of clippy brought a new rule and failed CI with no change of the code. A guard test checks the pin.

## Commits

`commitlint.config.ts`: Conventional Commits with a fixed list of scopes and a header of 100 characters at most.

`.gitconfig` at the root declares four config-based hooks (Git 2.54 or later). `bun run setup` includes that file in the configuration of the clone, one time per clone.

- `pre-commit` and `pre-merge-commit`: `bun scripts/private-files.ts` refuses a commit that holds a private file (see "Private files" below). It runs first.
- `pre-push`: `bun scripts/private-files.ts --pushed` refuses a push of a commit that holds a private file.
- `pre-commit`: `scripts/git-hooks/format-staged.sh` formats the staged files with Prettier and stages them again.
- `commit-msg`: commitlint refuses a message that breaks the convention.

## Private files

`scripts/private-files.ts` is the check that keeps private files out of this public repository. It cannot see the real vault, so its rules use structure:

1. No file of a folder named `.private`, `.content` or `.cache`, at any depth and in any letter case.
2. A vault file exists only in `fixtures/vault/`: a Markdown file (`.md`, `.markdown`, `.mdx`) that starts with a block of properties, a file of a folder named `.obsidian` or `.trash`, and a file that ends in `.canvas`, `.base` or `.excalidraw`.
3. Every file of `fixtures/vault/` is declared in `fixtures/catalog.json`.
4. No symbolic link.

What it cannot find outside the fixture vault: a note without properties, an attachment, and real text that someone pastes into a file. Care stays necessary.

It runs three times, and each run reads the files and the catalog from the place that it checks:

- Before a commit and before the commit of a merge: the index. A change of the work tree that is not staged does not count.
- Before a push: each commit that the push sends. A cherry-pick, a rebase and a commit from a clone without the hooks run no pre-commit hook, so the push is the last door of the machine. Only the last commit of each pushed branch is read, not the commits before it.
- In the tests (`scripts/private-files.spec.ts`): every file of the clone that git tracks or does not ignore. The test also checks that git ignores the private folders, and `.obsidian/` and `.trash/`, so that the fixture vault can be opened in Obsidian.

A clone where `bun run setup` did not run has no hook. CI then finds a private file only after the push.

A Markdown file with properties that is not a note (for example an issue template) needs an exception in the script. One exists (issue 41): a skill of this repository, `skills/<name>/SKILL.md` whose first property is `name: <name>`, for a name of the list `SKILLS` of the script, because the standard of the skills wants properties. The vault of the author holds many private skills in the same form, so a name that is not on the list, a deeper path, or another first line is refused.

## Fixtures and test stores

- `fixtures/` holds the fixture vault, its configuration and its catalog. `fixtures/README.md` has the rules.
- Prettier does not format `fixtures/vault/` (`.prettierignore`): the notes are test data, and their bytes must not change.
- `.gitattributes` gives every text file Unix line ends on every system. A Rust test checks it for the notes on Windows too, because the parity rule compares bytes.
- The test helpers make their folders in `.cache/test-stores/` of the clone, which git ignores.

## Corpus of full size

`bun run corpus` writes an invented vault of full size for prototypes and budget tests (`scripts/generate-corpus.ts`, with the generator in `scripts/corpus.ts`).

- Options: `--seed` (default 1, from 0 to 4,294,967,295), `--notes` (default 20,735, the number of public notes that the research counted) and `--out` (default `.cache/corpus/`). The vault is in the `vault/` folder of the output.
- The same seed and the same number of notes give the same files, byte for byte, on every machine. The generator reads no clock and no random source of the system, and it writes its images without a compression library. A test pins the digest of a small corpus.
- The numbers follow the public counts of `documentation/research/2026-11-17-current-state.md`. Tuned to the totals and checked by a test: the size of the notes (about 66 MB for 71 MB) and the number of links (about 154,000 for 155,000). Close to the counts: the shares of the note types, the notes with an image, with aliases, with a table, with a frozen list, with a code block and with a link to a heading, and the aliases that two notes share. The words are invented syllables.
- Four media notes in ten are stubs, with no text. No link goes to a heading of a stub.
- Name patterns: a dot, an ending like a file extension, an apostrophe, a character outside ASCII, an ampersand, a literal plus, a percent sign. No name holds a question mark, because Windows refuses it. No two notes share a file name, also when letter case is ignored.
- A corpus of full size is about 32,000 files. It is written in a few seconds.

Both corpus commands share the rules of their output folder (`scripts/output-folder.ts`):

- Inside the clone, the output goes below `.cache/`, `.content/` or `.private/` only: git ignores those folders, and the check of private files refuses every file of them. Another folder of the clone is refused, also when git ignores it.
- The output is never the clone, a folder that holds the clone, a folder that the command reads, a folder inside one, or a folder that holds one. Symbolic links are resolved before the comparison.
- A command writes over a folder only when the folder is empty or is its own earlier output: it holds the marker file of the command, and the marker names the command. Files that the user added to an earlier output are removed with it.
- A path that is a file is refused.
- The options are checked before the earlier output is removed.

## Published corpus

`bun run corpus:published --vault <folder> --list <file>` copies the files that the list names from a vault into `.cache/published/vault/`, with their vault paths (`scripts/export-published.ts`). The author runs it on his machines with the list of what Obsidian Publish serves today, so that prototypes and budget measurements use the real published notes (decision R30).

- The list: a file that ends in `.json` is the site cache of Obsidian Publish (a JSON object whose keys are the paths) or a JSON list. Every other file is text with one path per line. An empty list stops the command.
- The path of the vault and the list are inputs of the command. Neither is stored in this repository. The list of the author is in his private working files.
- The command never reads a file outside the vault. A path of the list that leaves the vault is not read, and a symbolic link that leads out of the vault is not followed.
- A file that is missing in the vault, that leaves the vault or that cannot be read is written to `missing.txt` of the output, and the command goes on.
- A file that the list names two times is copied and counted one time.
- The command never writes into the vault, and its output folder never touches the vault (see the rules above).
- Its marker file, `published.json`, holds the name of the command and three counts, and no path.
- The public CI never has the published corpus. Its tests use the fixture vault as the vault, with an invented list.

## CI

`.github/workflows/ci.yml` runs on each push to any branch.

- Job `checks`: dependency audit (level high, with one advisory ignored: the workflow file says which and why), type check, Astro check, lint, tests, format check, build of the site and of the plugin. The job has the Rust toolchain, because the parity tests build the Rust program.
- Job `rust`, on Linux and on Windows: format check, clippy, tests.
- Job `budgets`: the time budgets of the note page (`bun run budgets`), then the invented corpus (`bun run corpus`) and the budget of the first search on it (`bun run budgets:search`, R57, R63).

The public CI never sees the content store (BUILD-11 of the spec). It builds the empty site and, later, the site of the fixture vault.

## Container for local work

`Dockerfile` and `compose.yaml` at the root. `docker compose up` installs the packages and runs the dev server of the site on `http://localhost:4321`. `SITE_PORT` selects another port of the machine.

- The image holds Node and Bun only, in the versions of `.nvmrc` and of `packageManager`. A guard test fails when they differ.
- The source of the clone is mounted, so a change of a file shows at once. The packages live in two volumes, apart from the packages of the host.
- `.dockerignore` excludes everything: the image build gets no file of the clone, so no private file can enter an image.
- The port is published on the machine only (`127.0.0.1`).
- The container runs as the user `node` (id 1000), so that the files it writes into the clone have the owner of a normal Linux account.
- It is not an image for production. The plain server that serves the built site comes with the first slice (HOST-02 of the spec).
- CI does not start the container. It is checked by hand.

## Site

`apps/site/astro.config.ts`: Astro with Tailwind 4 through its Vite plugin. `src/styles/global.css` imports Tailwind. Prettier formats Astro components with `prettier-plugin-astro`.

- The variable `CONTENT_STORE` names the folder of a copy of the content store. The build reads the cleaned notes (`notes/`) as a content collection and the manifest (`manifest/`). The redirect list (`redirects.ts`: `redirectListFrom()`, `applyRedirectList()`) is described in "The redirect list" below. It reads nothing else, and never the vault. Without the variable the site has no note: that is the state of the public CI, which never sees the content store.
- One file per page (`build.format` is `file`). The page of a note is `-/note/<id>.html`, where the id is the identity of the note in the manifest. That name is plain ASCII on every system and on every host, whatever the name of the note is.
- The build writes the resolver map to `-/resolver-map.json` (`resolverMapOf` of `packages/resolver`, called by `apps/site/src/site-files.ts`): `pages` (the file of the page of each canonical path: the home page, each published note, each folder without a folder note, and the page with every backlink of a note that has one), `files` (`/robots.txt`, `/favicon.ico`, the sitemaps, the IndexNow key file and the Markdown of each note, with their kind: `text`, `icon`, `xml` or `markdown`), `attachments` (the key in the attachment storage of each hashed path of an attachment that a page uses), `folded` (the canonical path of each note and each folder, by the folded form of its text), `names` and `aliases` (the canonical paths of the notes of each file name and each alias, by its folded form), `choices` (the file of the "not found" page of each list of several notes), `notFound` (the file of the "not found" page), and `gone` (the addresses of the notes that the author unpublished, apart from the rest: the file of the gone page, and as sets of keys the canonical path and the Markdown path, the folded text, the folded file name and the folded aliases of each one; a key is 32 hexadecimal digits of the SHA-256 of the text, `goneKey()`, so the map holds no title and no alias of such a note; with `longest`, the length of the longest text, so that a longer text of a request is never hashed; decision R64). The build reads only the path, the aliases and the former paths of an unpublished entry. Its part `former` holds the former paths of the published notes in clear: they were public URLs. The map is for the resolver only: the host must not serve it. The attachments are not in the output of the build: the host gives them from the attachment storage.
- After each build, `src/map-parts.ts` cuts the resolver map into parts (issue 121, R94): a head `-/resolver-map/head.json` (what is not a key: the lengths, the lists, the files of the error pages, the count of the parts) and parts `-/resolver-map/<n>.json`, each with the entries of every record whose key has that part (`partOfKey()`: FNV-1a of the key, modulo the count, a power of two that keeps a part near 32 KB). The Worker and the plain server read the head at their first request and a part when a request needs it (`partedResolver()` of `packages/resolver`), and give the answers of the whole map. The whole map stays in the output for the checks of the build and the tests; the deployment does not upload it (`.assetsignore`).
- The generated files live under `-/` (URL-08): `-/md/<id>.md` (the Markdown of a note: its cleaned note, URL-10), `-/folder/<id>.html` (the list of a folder without a folder note, URL-16; `noindex, follow`, no canonical link, R85), `-/choice/<id>.html` (the "not found" page of a name or an alias of several notes), `-/backlinks/<id>.html` (the page with every backlink of a note with more than 50 backlinks, at `/-/backlinks/<id>`, where the id is the identity of the note; `noindex, follow`, no canonical link). The id of a folder or of a list is 16 hexadecimal digits of the SHA-256 of its vault path, or of the vault paths of the list joined with line feeds. `404.html` is the "not found" page, `410.html` the gone page (NAV-19: it shows nothing of the removed note, and its search field starts empty), `500.html` the server error page (NAV-20: one file with its style inside it, no script, no font, in the mode of the system; the integration `selfContainedPages()` of `src/self-contained.ts` puts the style sheets into it after each build and stops the build when it still names another file of the release, or when a `meta` element has an `http-equiv` other than `content-type`, such as a refresh, or is not closed), `robots.txt` the rules for robots (`src/robots.ts`, issue 54: one group that allows every crawler on every URL, the line `Content-Signal: search=yes, ai-input=yes` and the line of the sitemap index; the same file on every host), `sitemap.xml` the sitemap index and `sitemap-<group>.xml` one sitemap file per group of note types (`src/sitemaps.ts`: the groups of seo item 35, `sitemap-notes.xml` for the other notes and `sitemap-generated.xml` for the indexable generated pages; every note but the ones with `publish_noindex: true` (R85: their page says `noindex, follow`), with its `updated` property as `lastmod`, else the time of its last publication (R85: a date more than one day after that publication is a typo); a generated page has no `lastmod`), `<key>.txt` the IndexNow key file (`src/indexnow.ts`: the key is public by design, and the name is a reserved root name because it ends with `.txt`). The three error pages are `noindex, follow` and have no canonical link. `favicon.ico` (16 and 32 pixels) comes from `apps/site/public/`, which Astro copies to the root of the output.
- The head of every page (`src/layouts/Page.astro`, issue 133): the icon of the site, which is the mark of the main site (`/favicon.ico` with `sizes="32x32"`, the vector icon `src/icons/icon.svg` and the icon of a home screen `src/icons/apple-touch-icon.png`, 180 pixels; the build names the last two with a hash under `/_astro/`), the color of the bar of the browser in each mode (two `theme-color` elements with the surface of the header, `BAR_COLORS` of `src/styles/themes/knowii-bar.ts`, and the media query of the mode of the system, `BAR_MEDIA` of `src/mode.ts`; the script of the mode gives the element of the mode that the page shows the media `all` and the other `not all`, so the bar follows a mode that the reader chose), the author, the name of a home screen (`apple-mobile-web-app-title`), and on a page with a canonical link the text of a card of a shared page (`og:site_name`, `og:type` `website`, `og:title`, the title without the site name, `og:description`, `og:url`, the canonical URL, `twitter:card` `summary`, and the account of the author on X). The image of a card comes with issue 54, the web app manifest with issue 109. The server error page loads no other file (NAV-20): it has the colors of the bar and no icon link. The header shows the same mark as its logo, before the site name (`src/components/Header.astro`): the vector icon written into the page at 32 by 32 pixels, hidden from assistive technology, so the site name is the name of the link, the logo costs no request and moves nothing, and the server error page keeps it. It has its own background, so it is the same in both modes.
- The checks of the build (`src/site-checks.ts`, `src/search-signals.ts`, issue 54) stop a build where an indexable page has not one canonical link, an `og:url` that is its canonical link, an `og:title` and a `twitter:card`; where a canonical link or a URL of a sitemap does not lead through the resolver to its page with no redirect, or is not on the canonical origin without a query; where a URL of a sitemap is not an indexable page that names itself, or is listed twice; where an indexable page is in no sitemap; and where the sitemap index does not name the sitemap files of the resolver map. The Markdown form of a note answers `X-Robots-Tag: noindex` and `Link: <canonical URL>; rel="canonical"` (IDX-16).
- Each page has a canonical link to its canonical URL on `https://notes.dsebastien.net` (`site` of `astro.config.ts`), so a URL with a query shows the same page with a clean canonical link (URL-12). The layout is `src/layouts/Page.astro`.
- An attachment has a hashed URL, `/-/attachments/<key>/<name>` (the first part of URL-15): the key of the file in the attachment storage, then its file name, percent-encoded. `attachmentPath` of `packages/resolver` makes it. The stable URL that follows the vault path comes with the slice of the URL contract.
- The page of a note shows an embed of an image as an image, with the width and the height of the manifest entry (an embed with `|300` or `|300x200` gives that size), lazy loaded. An embed of a video or of a sound gets the player of the browser. An embed of another file, and a link to a file, are a link to its hashed URL. A Markdown image is an embed whose alternative text is its text. The kind of a file comes from the end of its name.
- The build reads the properties of a note from its cleaned note (`apps/site/src/note-properties.ts`), with the YAML reader and the options of Astro but for its tag for dates: a date stays the text of the vault, so the panel and the title band show the day and the time that the vault writes, in no other time zone.
- A note page under its title band (issue 48, R59): the properties panel (every property of the note, by the display rules of the site of today; a link of a property is a link when its target is published), the text, and the backlinks (the notes that link to the note, the newest update first, each with the sentence around its links; 50 at most, the rest on the page of the backlinks). A note with 3 headings or more of levels 1 to 3 has an outline. On a wide screen the outline is in a left rail (from 1024 px) and the panel in a right rail (from 1280 px); on a smaller screen each is a folding block above the text. The panel is closed in the HTML; its script keeps the choice of the reader in the storage of the browser (key `properties`), and the key `p` opens and closes it.
- `packages/resolver` holds the URL functions (`canonicalPath`, `folderPath`, `markdownPath`, `attachmentPath`, `tagPath`, `backlinksPath`), the map of a site (`resolverMapOf`, `foldersOf`, `choicesOf`) and the resolver (`resolve`). The rules of the resolver are in the section "The URL contract" below. The first redirect list comes with issue 44. `errors.ts` gives the form of an error answer (`errorFormat()`) and its short Markdown text (`errorText()`, NAV-21). The origin of the absolute addresses of that text is `Release.origin` when the host gives one (the plain server gives its listening address), else the origin of the URL of the request, which only the Worker uses: the host gives it only the requests of its own names. It never comes from a header of the request (issue 102). `handler.ts` gives the answer of a request (`siteHandler()`, with the port `Release` and its files `StoredFile`, `failureResponse()` and `ASSET_FOLDERS`): the URL contract over HTTP, with no knowledge of a host, and the deployment record `/-/deployment.json` (`DEPLOYMENT_RECORD_FILE`, STORE-08), which the deployment writes into the output after the build and every host gives with `Cache-Control: no-store`. `map.ts` checks the shape of a resolver map that a host reads (`resolverMapFrom()`, `RESOLVER_MAP_FILE`). Two adapters give the handler its files: the plain local server (`apps/site/server/serve.ts`, from folders) and the Worker of the host (`apps/site/worker/worker.ts`, from the static files of its Worker version through the binding `ASSETS`, and from the object storage through the binding `ATTACHMENTS`). The Worker reads the resolver map and the server error page of its release at the first request of an isolate. A read that fails for a reason that can be short (a fetch of `ASSETS` that fails, or a status 5xx) is done again at once, one time, after a pause of 50 ms, so a short failure of `ASSETS` does not reach a reader (issue 128). The whole read, both reads and the pause between them, has a time limit of 5 s (`READ_TIME_LIMIT`, issue 129): a read that never settles does not keep every request of the isolate waiting. The limit runs from the start of the shared read. Each request that waits for it has a timer of its own to the same end, because the timer of a request that the host cancels may never fire. Past the limit, the request answers 500, the read goes no further (no report of a first failure, no pause, no second read), and the next request reads again at once: a time-out does not start the ten seconds below. A read that settles after the limit of one request still gives its result to the requests that wait, and the Worker keeps it. The request that starts the read keeps it alive with `ctx.waitUntil()`. What a cancelled first request still costs: the host keeps a `waitUntil()` promise only for a limited time after the request ends, so its read can still stop; the requests that wait then answer 500 at the limit, and the next request reads again. A missing resolver map, a resolver map that is not JSON or not a resolver map, and any other status fail at once. After a read that fails, it answers 500 and waits ten seconds (`RETRY_AFTER`) before it reads again, not at each request: the resolver map is large. Each failed read goes to the log of the host (the first of two reads as "first read of the release failed, reading it again", with the failure as its cause), never into an answer.
- The network behind the hero of the home page (issue 81): `src/components/NetworkBackground.astro` is a canvas that covers the hero (`absolute inset-0`, so it takes no space and moves nothing), with `aria-hidden`, no pointer events, and the class `print:hidden`. Its script is one module file (`src/background/network-layer.ts`, with the pure parts in `src/background/network.ts`) with no dependency. It starts after the load of the page, in an idle moment. The layout is seeded pseudo-random (a few dozen nodes, by the area of the hero, each linked to its 2 nearest neighbors), and each node drifts slowly around its place. The color is the token `secondary-text` of the mode, which the script reads from the class of the canvas when it starts or resizes and again when the mode changes, never at each frame. The script draws one still frame when the reader asks for less motion, and moves only while the page is shown and the hero is on screen (`IntersectionObserver`; a layer that is hidden or off screen keeps its last frame, and one that starts off screen fades in when it comes on screen), at 30 frames per second at most and with a device pixel ratio of 1.5 at most. Behind each line of the text marked `data-network-quiet` the layer is cut down, so that no pixel keeps more of the color than the quiet limit of the mode (`LAYER` of `network.ts`): `network.spec.ts` checks with the values of the theme that the text over it passes WCAG AA in both modes. The title band of a note page has no network: the note page keeps its budgets and its reader's attention on the text.
- `bun run site:fixture` publishes the invented notes of a copy of the fixture vault into a content store in `.cache/`, builds the site from it and serves it on `http://127.0.0.1:4322` (option `--port`). With `--sample` the vault also holds the budget sample (a long note with a long outline, a media note, a hub note with 489 backlinks), and the command prints the addresses of those three pages. Ctrl+C stops it and removes its folders. A second publication unpublishes one invented note that no note links to (`10 Garden/Bean trellis.md`), a takedown removes another one with the sound file that only it uses (`50 Field guide/Embeds/Embed of a sound.md`), and the command prints their addresses (the gone page, 410, and the "not found" page, 404) and the file of the server error page, which a working server never gives. Use it to look at the site with notes, attachments, folders and redirects; it never reads the real vault.
- `bun run urls build` publishes the invented notes of the URL table (`fixtures/urls.json`) from a copy of the fixture vault and builds their site into `.cache/url-table-site/` (`dist/` is the output for a host, `notes/` the cleaned notes; the command removes only an output of its own). `bun run urls check --base <address>` asks a host for every case of the table and for two files that did not change (304, URL-18), prints what has a finding and ends with the code 1 when there is one (SEAM-04, HOST-02). The tests run the same cases on the plain local server and on the Worker (`apps/site/src/urls-page.spec.ts`), so a preview host, a test host and a server of the exit path are all checked with one table. `bun run urls parity --base <address>` is the URL parity test (story 161, RES-06; issue 60 runs it before the switch): see "The URL parity test".
- `bun run serve` starts the plain local server on `http://127.0.0.1:4322` (`apps/site/server/serve.ts`, options `--dist`, `--port` and `--attachments`). It answers through the resolver, with the map in parts as the Worker reads it (issue 121): 200 with the page or the file, a redirect with its `Location` and its `Cache-Control`, or 404 with the "not found" page (a redirect keeps the query of the request). A page and a file have an `ETag` of their size and their time, `Cache-Control: public, max-age=0, must-revalidate`, and answer 304 to a request whose `If-None-Match` names that tag (URL-18). The header is read as a list of quoted tags, so a tag that holds a comma is one tag (issue 117); `*` counts only as the whole header, and a header that is not such a list names no tag. A "not found" answer has `Cache-Control: no-store`. An address of an unpublished note answers 410 with the gone page, `no-store` too. Every error answer (404, 410, 500) has `Vary: Accept`, and its form follows `errorFormat()`: a path under `/-/md/`, or an `Accept` header that prefers `text/markdown`, gets the short Markdown text of `errorText()` with the same status (NAV-21); the 404 text of a name of several notes lists them. Each address is a Markdown link whose destination is between angle brackets and whose text has its marks escaped, so a name with a parenthesis or a `*` keeps its link whole. `text/markdown` and its older name `text/x-markdown` are one type: the weight of `text/markdown` counts, and `text/x-markdown` counts only when the header does not name `text/markdown`, so a refusal of `text/markdown` stays a refusal. Its absolute addresses name the listening address of the server (the `origin` of `Release`), never the `Host` header of the request, which the client chooses (issue 102). A request whose URL does not parse (a `Host` header such as `[bad`) answers 400 with `no-store`. A page or a file that the resolver map names and that the output of the build lacks answers 500 with `no-store` (URL-33): the release is broken. With `--attachments <folder>` (the attachment storage), it gives each attachment of the resolver map from that folder, by its key: with its kind from the end of its name, a cache time of a year, no right to run a script (`Content-Security-Policy` with `sandbox`, but for a PDF, which the viewer of a browser refuses in a sandbox, and `nosniff` for every file), and the part that a range request asks for (206, or 416 for a range outside the file; several ranges get the whole file) (HOST-05). An attachment of the map that the folder lacks answers 500 with `no-store` too (URL-33). It also gives the files of the `_astro/` folder of the output (the style sheets, the icons), from a list that it reads one time at its start, with their kind and the cache time that the host gives them: a year (`public, max-age=31536000, immutable`) for `_astro/`, whose names hold a hash, a check at each use for the files of `-/search/`; a file of that list that is gone answers 500. `/favicon.ico` is a file of the resolver map (`image/x-icon`, its `ETag`, a check at each use). Every 500 is the server error page, which the server reads at its start (so a release that lost it still gives it), with no detail of the failure (NAV-20), also for a failure of the server itself; a build without that page gives the short text as plain text. The file of a response comes from the resolver map or from that list, never from the request. It is not a server for production.
- The search (issue 51, R63): the page `/-/search` (`-/search.html`, `noindex, follow`) runs `src/search/search-page.ts`. The build writes the title index to `-/search/titles.json` (the keys of its parts, and the canonical paths of the notes with `publish_noindex`, which the random note of the command palette leaves out) and `-/search/titles/<key in hexadecimal>.json` (the parts, from `src/pages/-/search/titles`), and the integration `searchIndex()` (`src/search/search-index.ts`) writes the full-text index of the note pages with Pagefind to `-/search/pagefind/` after each build. The plain server gives the files of `-/search/` as it gives the files of `_astro/`. The dev server (`bun run dev`) has no full-text index, because the integration runs after a build only: on it the full text of the search page says that it could not load; build the site and serve it to try the search. `bun run budgets:search [--vault <folder>]` builds both indexes of a vault (the invented corpus by default) and fails when one search loads more than 350 KB (R63: the keys and every part of the title index that the letters of the query load, and the full text of the query with 10 results); it also reports the session of a reader who stops after each letter. It prints numbers only. The numbers are in `documentation/research/2026-11-22-search-index.md`.
- The command palette (issue 122, R93): the loader `src/palette/loader.ts` (through `components/PaletteLoader.astro` in the header, on every page but the server error page) imports `src/palette/palette-bundle.ts` at the first opening: the palette (`palette.ts`), its style (`palette.css`, as text) and the code of the search. Its commands are in `src/palette/commands.ts`, and the paths that it opens in `src/palette/site-paths.ts` (checked against the resolver by a test). Its full text needs a built site, as the search page.
- The store catalog (issue 56, BUILD-06, CAT-01): the variable `STORE_CATALOG` names its source, a file or an https address of `products-light.json` (another address is refused; a read has a time limit of 10 s). `bun run deploy` sets it to the live catalog (`STORE_CATALOG_URL` of `apps/site/src/site.ts`, the `www` host of the store) unless the variable names another source. The build reads it one time (`readStoreCatalog()` of `apps/site/src/ads/catalog.ts`): a product with a broken `id`, `name`, `href` or `tags` is left out and the others stay, as on the current site. A catalog of the live address with no break becomes the last valid copy, `.cache/store-catalog.json` of the site, or the file that `STORE_CATALOG_COPY` names; a file never does. When the catalog cannot be read at all, the build uses that copy for 7 days after its `generatedAt`, and else shows no product ad. Each reason is a line `[store-catalog] ...` of the output of the build, and of the file that `STORE_CATALOG_REPORT` names: `bun run deploy` puts those lines in the warnings of its result line (the port `buildWarnings` of `deployRelease()`). Without `STORE_CATALOG` the build has no catalog and no ad, which is the state of the public CI.
- The ad at the end of a note (issue 56, AD-01, AD-02): `apps/site/src/ads/matching.ts` picks two products at most, `components/Ad.astro` shows them after the text of the note as text cards (no image: a note page loads nothing from another host, PERF-27), and the inline script `ctaScript` of `ads/cta.ts` sends `cta_clicked` through `window.plausible` when the page has it (issue 57).
- The build stops when the content store cannot be trusted: `CONTENT_STORE` names no folder, a file of the manifest is not an entry, the id of an entry is not 16 hexadecimal digits, or two entries have the same path.

## Deployment

A release goes to the host from the machine that publishes, never from the public CI (BUILD-02, BUILD-11, R76). The names of the host (the account, the Worker, the object storage, the host name, the zone) are in a private target file, never in this repository.

- `bun run deploy --target <file> --content-store <folder> --attachments <folder> [--takedown] [--new-content-store <host name>]` builds the site from the copy of the content store on this machine (`CONTENT_STORE`: the build reads it and never writes it) and deploys it (issue 32). The publishing tool runs it after its push, with `--from-main`, in a clean clone of this repository that serves only for the deploys. `--dist <folder>` deploys an output that is built already, and touches no attachment. The command refuses a folder that is not the output of a build (no resolver map, `checkOutput()`), before it writes a file into it: the whole folder goes to the host. `--dry-run` reaches no host and needs no token: no attachment moves, and wrangler checks the bundle and uploads nothing. With `--content-store` it needs no `--attachments` and checks no key. A dry run never counts as a deployment: its result says `"deploy":"skipped"`. The logic is `deployRelease()` of `apps/site/worker/release.ts`; `scripts/deploy.ts` gives it the real steps. The steps:
    1. `--from-main`: the clone must have no change and be on `main` (else it stops with a message). It runs `git fetch` and `git pull --ff-only`, stops when `HEAD` is not `origin/main` then, and runs `bun install --frozen-lockfile`, then the command again without the flag, so the code after the pull runs. Without the flag, none of this happens (a clone for development).
    2. The copy and the live release. The copy of the content store must be clean (no change of a tracked file, no new file) and at the `main` of the content store after a `git fetch` of the copy (`checkContentCopy()` of `apps/site/worker/content-copy.ts`). That fetch writes only a ref of its own, `refs/deploy/origin-main` (`--refmap=`), and `git status` runs with `GIT_OPTIONAL_LOCKS=0`, so the deploy writes nothing that the fetch, the push or the index of the tool uses: the keys and the build come from that commit, so the record names what the build read. Then the command reads the record of the live release. When it has a content revision, that revision must be the commit of the copy or one of its ancestors (`descendsFrom()`, `git merge-base --is-ancestor`), so a takedown never comes back with older content. A live revision that the copy does not know is a refusal with a message, and so is a host whose record cannot be read (a status other than 200 and 404, no network). A host with no record (404, a first deployment) takes any release. `--dist`, with no content revision, is refused when the live record has one. `--new-content-store <host name>` moves the host to another content store (issue 127), for example from a test content store to the real one: the author gives the host name of the target again (another name stops the command, and its message does not print the host), and the live content revision must be one that the copy does not know. A copy that is only behind does not know it either, so the command asks the content store of the copy (`contentStoreHas()`, a fetch of that one commit that writes no ref): when the content store has the revision, when it cannot say (no network, a shallow copy), or when the copy knows the revision (in its history: the same store; outside it: other content of the same store), the move is refused. It is also refused when the host has no release of a content store, with `--dist` and with `--takedown` (these two also in a dry run). A dry run reads no live record, so it checks nothing else. The command prints the live content revision that it replaces. The publishing tools never pass it. A test content store must not be a GitHub fork of the real one: GitHub serves each commit of a fork network from each of its repositories, so the move would be refused. Right before `wrangler deploy`, the command reads the live record again and refuses when another release went live during the build, and checks that the copy did not move. A refusal deletes nothing, also after a takedown, since a newer release can be live.
    3. The attachments (decision 1 of the comment of 2026-11-25 on issue 32): the keys that the release uses are the keys of the attachments of the published entries of the manifest of the copy (`usedAttachmentKeys()`, with the reader of the build), less the keys of `withdrawn.json` of the copy (`withdrawnAttachmentKeys()`, issue 120: the files that the guards withdrew; a file that the tool would refuse stops the command before its first step). The command reads `withdrawn.json` before any other read of the copy, and deletes the withdrawn keys from the object storage right after it reads the live release, before its check: a refused run, and a run whose read of the keys of the release or of the history fails, still deletes them. When the copy does not know the live revision (a newer release of another machine can be live), it refuses with no deletion. With `--new-content-store`, the deletion comes after the check of the move; a failure of `descendsFrom()` deletes nothing before the check. The command fetches the copy first (a fetch that fails refuses with no deletion), reads `withdrawn.json` at the commit of the copy, and gives the check of a clean copy at `main` (`inspectContentCopy()`) to the run: a copy with changes or behind its content store is refused after the withdrawn keys left, when the copy is at the `main` of the content store or descends from the live revision (`descendsFrom()` true: a newer live release whose commit the fetch brought is not enough). When the keys of the new release cannot be read (a broken manifest at the commit of the copy), the command still deletes the files of every removal of the history (those that the live release holds too, with no filter of a release), or, when the history cannot be read either, every file that the live release does not use; then it stops with a warning that a file can still be public. After the check of the live release, it lists the object storage and deletes the other forced files (issue 120, decisions of the author R78): the keys of the notes that a takedown or a forced removal took away in the whole history of the copy that the release does not use (`removedAttachmentKeys()`: every manifest entry that a commit deleted, whatever its subject says, read at its parent, but an unpublished entry whose path a move of the same commit took: a published entry of that commit that held another path at the parent and names it in `formerPaths`; an entry with no `attachments` uses no file; a deleted file that is no entry at the parent gives the keys of the newest older version of it that is one, or no key and a warning when none is; a file of `manifest/` whose name has a control character gives a warning and no key; a merge commit deleted every entry that one of its parents has and that it has not, read at that parent). When the history cannot be read (a shallow copy, an error of git), the command fails closed (decision of the author of 2026-11-26): it deletes every file of the object storage that the new release does not use, as on a first deployment, with a warning that names the cause, and goes on; it never stops before that step because of the history. Only the removals that the live release does not hold beat every release; the files of a removal that it holds leave when neither the new release nor the live release uses them, also when a later step fails, so a later note that uses such a file openly keeps it. A file that the new release uses is never forced, but a withdrawn key always is. Those files leave at once, also when a later step fails; a deletion that fails ends the command with a failure, after the release, and a warning that a file can still be public. Then it uploads each used key that the storage lacks from `<attachments>/<key>`, the attachment folder of the machine; a withdrawn key is never uploaded and never counts as missing. A key in neither place stops the command before the build, with the keys (never a vault path), and so does a file of the folder whose SHA-256 is not its key. A file of the folder above the size limit of an attachment (100 MiB, issue 72) stops the command before the build too, with its key and its size: its size is read, never its bytes, and no file is uploaded. The publishing tool never holds a key of the object storage. Then the variants of the images (issue 87, PERF-25, R92): each image of the release whose pages offer variants (`releaseImages()`: a JPEG, PNG or WebP wider than 480 pixels, by the name and the size of the manifest, with the rule of the build, `imageVariants()` of `packages/resolver/src/variants.ts`) gets one WebP file per width (480, 800, 1200 and 1600 pixels, the last one at its own width when it is narrower), named `<key>-w<width>-<generation>.webp` in the object storage beside its image. The object storage is the cache: a variant that it has is never made again, and an image whose variants it has is never read. Each missing variant is made from `<attachments>/<key>` on this machine (`makeVariants()` of `release.ts` with `encodeVariants()` of `apps/site/worker/image-variants.ts`: sharp, WebP at quality 75, with no metadata; a JPEG is turned as its Exif says, as the plugin reads its size, and no other kind is; an image with frames keeps them; the image is read and resized one time to the largest variant, and the smaller ones are made from it), the images of more than 16 million pixels one at a time and the others four at a time, and uploaded before the build. A variant never blocks a deployment (review round 1 of issue 87): an image whose file is not in the folder, is above the size limit, is not the file of its key, is cut or cannot be decoded, and a variant that cannot be uploaded, give a warning in the result with the name and the key of the image, and its pages give the file of the image in place of the missing variant (the URL contract below). An image of more than 50 million pixels gets no variant, with a warning; sharp never reads more pixels (`MAX_VARIANT_PIXELS`). A takedown makes no variant, and neither does a deployment that counts as one (a forced removal since the live release). The kind of an image is read from its bytes: a file that is not a JPEG, a PNG or a WebP, whatever its name says, and a PNG or a WebP with an Exif turn (the plugin reads its size as stored), get no variant, with a warning. An animated PNG (an `acTL` chunk before its first `IDAT`) gets no variant either, so its page keeps the file that moves. sharp loads one time, at the first encode: when it cannot load on this machine, the run stops encoding after the first failure, with one warning that counts the images left. A deployment encodes for 10 minutes at most (`VARIANT_TIME_LIMIT`); the images that wait give one warning and get their variants at the next deployment. Run `bun run variants --target <file> --content-store <folder> --attachments <folder>` once before the first deployment after this change, and after a change of `VARIANT_GENERATION`: it makes the variants that the object storage lacks, under the lock of the deployments of the target and from a copy clean and at `main`, with no build and no deployment, with no time limit, and deletes nothing. The deployment record names the generation of the variants of its release (`variants`); the cleanup keeps a variant of a kept image only in this generation and in the generation of the release before, so the variants of an older generation leave after one more release. A variant follows its image in every other step: the command reads each name of the object storage as the key of its image (`imageKeyOf()`), so the withdrawn keys, the files of a takedown or a forced removal and the cleanup take the variants of every generation with their image, and keep them for the release before; a deletion without a list of the object storage (the withdrawn keys, the removals when the keys of the release cannot be read) deletes every name that a variant of the key can have (`variantKeysOf()`). A variant does not count as a name that is not a key. A dry run makes no variant.
    4. The build (`bun run build:site`), then the whole `_headers` file (`headersFile()`), the `.assetsignore` file that keeps the whole resolver map on the machine (issue 121) and the deployment record (`/-/deployment.json`, STORE-08: `contentRevision`, the commit of the copy, `null` with `--dist`; `siteRevision`, the commit of this clone; `builtAt`, the time when the build ended, in UTC to the second; `previous`, the same three fields of the release that was live when this one was deployed, or `null` when the host had no record; `newContentStore: true` only in a release that moved the host to another content store; `variants`, the generation of the image variants that its pages name, issue 87) into the output. Then the limits of the host (BUILD-08, `checkOutputLimits()` and `HOST_LIMITS`): at most 100,000 files in one Worker version and 25 MiB per file. A release above a limit stops before the deployment, with the count of each class of files (the first folder, two levels under `-/`) or the names of the large files.
    5. `wrangler deploy` with the wrangler configuration below: one new Worker version, one switch.
    6. Live: the command reads `https://<host>/-/deployment.json` until it gives the record of this build on 3 reads in a row, 1 second apart, 30 reads at most (`LIVE_CHECKS`): after a switch, the old and the new release answer in turn for some seconds. A host that does not give it is a warning, not a failure.
    7. The cleanup of the object storage after a deployment that succeeded and that the host gives (step 6; a release that was not seen live deletes no other file than the forced ones, with a warning, since the release before can still be live): each object whose name is a key (64 small hexadecimal digits) and that neither the new release nor the release before it uses is deleted, so one revert keeps its files (issue 120). The keys of the release before are the keys of the published entries of the manifest at the content revision of the live record that this release replaced, read from the copy with git and the reader of the build (`releaseAttachmentKeys()`), less the forced keys. On a first deployment, and on a move to another content store (a revert across it is refused), only the files of the new release stay. When the live release was built from an output (`--dist`) or git cannot read its revision, only the forced files leave, with a warning. A name that is not a key stays, with a warning that gives only how many there are: such a name can be a path of the vault, and the result goes to the tools and to an agent. After a takedown, such a name and a list of the object storage that fails end the command with a failure and a warning that a file can still be public, as the takedown of the tool does. `deleted` counts the objects that the storage still had. A cleanup that fails is a warning, but after a takedown it fails the command. A failure of a step deletes no other file than the forced ones of step 3 (decision F4 of the author on issue 120): after a takedown whose build or deployment failed, the files of the taken-down notes are gone, and the old files that the live release uses for other notes stay. A file that a taken-down note shared with a note that only the live release uses goes too (business rule 16). A deletion of a forced file that fails fails the command in every run (step 3). With `--takedown`, a release that was not seen live fails the command: the pages of the takedown must be gone. A run whose copy holds, after the content revision of the live release, a commit that took an entry away (`removalsBetween()`) counts as a takedown in the same way, with a warning that names the subjects of those commits, also without `--takedown` and from any machine: a forced removal sets no marker of the tools, and every later deployment counts as a takedown until a release that holds it is seen live. When the copy cannot say, the run counts as a takedown too.
- What the command prints: the output of `git pull`, `bun install`, the build, wrangler and the restarted command comes on the standard output before the last line, and the errors on the standard error. When the restarted command of `--from-main` ends with no result line (it could not start), the wrapper prints one itself: `build` and `deploy` are `skipped`, `live` is false, `contentRevision` is `null`, `uploaded` and `deleted` are 0, and `error` says `the deployment ended with the code <n> and no result`.
- One deployment at a time per target on a machine: the command and `deploy:revert` take a lock file of the clone, `.cache/deploy/<worker>/lock` (`takeDeployLock()` of `apps/site/worker/deploy-lock.ts`), holding the process and the start of the run. It is written whole into a temporary file, then linked to its name, which fails when a lock exists, so a lock is never half written. Both faces of one machine must use the same clone of the site code: the lock is in that clone, and two clones would not see each other. It covers the whole run, from the steps of `--from-main` and the first list of the object storage to the cleanup, and goes at the end, also after a failure. A second run stops with a message while the first one runs; a lock whose process is dead, or that is older than the most time limit of a deployment and one hour (`STALE_AFTER_MS`: 25 hours, for a process number used again after a reboot), is taken over with a warning. The runs that read one stale lock race for one claim of its takeover (`.takeover-<digest of the lock>`, made whole like the lock): only the run with the claim takes the stale lock away and makes its own, and a run moves a lock only when it is the stale one that it read, except when the holder of an over-25-hour lock releases it in that moment, so any number of runs that take over one stale lock at once end with one holder (issue 126). The claim of a run that stopped during its takeover (its process is dead, or it is older than one minute) goes at the next try, and the run that saw it gives way. With `--from-main`, the warning of a lock that was taken over reaches the `warnings` of the result line of the restarted command. The restart of `--from-main` runs under the lock of its parent. So the plugin and the command line program never deploy at once from one clone.
- Each target has its own object storage (one per target, the field `bucket` of the target file): the cleanup of a target deletes every key that neither its own release nor the release before it uses. Between two machines no lock exists. Two deployments of one target from two machines can still meet: the one whose copy is older can delete a file that the newer release of the other uses, between its list and its cleanup. The check of the live release narrows it: a deployment whose content does not descend from the live content stops before anything, and so does one that sees another release go live during its build; a failed deployment deletes only the forced files. It does not close it: two machines that deploy one target at the same time can still put older content live after a takedown, or let one machine delete a file that the newer release of the other uses. A deployment from a copy that is newer than the live release but older than the last publication reads an older `withdrawn.json` and can upload such a file again until the next deployment of a newer copy. Issue 125 holds the lock on the host. Until then, publish from one machine at a time.
- The result for the publishing tool (PUB-42): the last line of the standard output is `DEPLOY-RESULT ` followed by one line of JSON (`resultLine()`), also when the command stops before its first step (`stoppedResult()`; with `--takedown`, such a stop, for example a copy with changes or behind its content store, warns that a file can still be public: the tools never pull the copy, decision R65):

    ```
    {"build":"ok"|"failed"|"skipped","deploy":"ok"|"failed"|"skipped","live":true|false,"url":"https://<host>/","contentRevision":"<sha>"|null,"uploaded":<n>,"deleted":<n>,"warnings":["..."],"error":"..."|null}
    ```

    `build` is `failed` also when the output breaks a limit of the host; `live` is true when the host gave the record of this build; `contentRevision` is the commit of the copy (`null` with `--dist` and when the command stops before it reads the copy); `url` is empty when the host is not known (the target file cannot be read, or the arguments cannot be parsed); the command reads the target file first, before the steps of `--from-main`; `error` is `null` only when the command succeeded. The exit code is 0 only when `error` is `null`.

- The token: `NOTES_DEPLOY_CLOUDFLARE_API_TOKEN`, else `CLOUDFLARE_API_TOKEN` (`deployToken()`). The command gives it to wrangler as `CLOUDFLARE_API_TOKEN` and uses it for the object storage. `git pull`, `bun install` and `bun run build:site` run without every variable whose name holds TOKEN, SECRET, KEY or PASSWORD, in any letter case (`withoutTokens()`): they run code of packages, and must get no secret of the machine. The publishing tool starts the command with `bun --env-file=<file>`, so the value comes from a private `.env` file outside this repository.
- `bun run deploy:revert --target <file> --content-store <folder>` goes back to the Worker version before the live one (`wrangler rollback`, BUILD-07), then reads the deployment record until it gives the record of the release before on 3 reads in a row (`revertRelease()`) and prints which commit of the content store is live. The record of each release names the release that it replaced (`previous`). The command refuses a live release that names none (a release deployed before `previous` existed, or the first release), and a revert across a takedown or a forced removal: a commit of the copy, after the content revision of the release before and up to the live one, that took a manifest entry away (`removalsBetween()`, read from the content of the commits, whatever their subjects say, issue 120) would bring a removed note back. A merge commit between the two releases is a refusal too: the revert fails safe. It also refuses a live release that moved the host to another content store (`newContentStore`), since the release before has other content. Then deploy a new release instead. The copy must be clean and at the last `main`, as for a deployment. The cleanup of each deployment keeps the files of the release before it, so a revert gets back its pages with their files (issue 120), but not the files of takedowns and of forced removals (a revert cannot cross those commits) nor the files of `withdrawn.json` (a revert does not bring them back).
- The target file is JSON: `accountId`, `worker`, `bucket`, `host`, `zone`, `noindex` (`targetFrom()` of `apps/site/worker/deployment.ts` refuses a wrong or unknown field). The host is always a route of `zone` (`<host>/*`): a custom hostname of that zone (Cloudflare for SaaS), or a name of the zone with a proxied DNS record. Never a custom domain: wrangler replaces the DNS record of a custom domain without a question when it runs with no terminal, so a wrong host would take over a live name.
- The command writes the wrangler configuration into `.cache/deploy/<worker>/wrangler.json` (`workerConfiguration()`: the static files give a file only by its exact name, with `html_handling` and `not_found_handling` set to `none`: with another value the static files redirect the `.html` paths, such as `500.html`, and the folder paths, such as `/_astro/sub/`, and the Worker answers 500 for every redirect of the static files and passes none on (issue 117); the Worker runs first for every path but `/_astro/*` and `/-/search/*`, the binding `ASSETS`, the binding `ATTACHMENTS` to the object storage, no `workers.dev` address and no preview address), and the whole `_headers` file into the output, over any file of that name (`headersFile()`: on every host the files of `/_astro/`, whose names hold a hash, get `Cache-Control: public, max-age=31536000, immutable`, since the host gives them `max-age=0, must-revalidate` by default). Then it runs `wrangler deploy` (the version in `apps/site/package.json`).
- A preview host (`noindex: true`, IDX-26): the Worker sets `X-Robots-Tag: noindex` on every answer (its variable `NOINDEX`), errors and 304 included, and the `_headers` file sets it on every static file, which covers the files that the host gives without the Worker (`/_astro/`, `/-/search/`).
- The search engines (issue 54, `searchHostOf()` and the step 6 of `deployRelease()`): right before the deployment, the command reads the live sitemaps (a `<urlset>` at `/sitemap.xml` is read as the one sitemap, never as an index); once the release is seen live, it compares the live `robots.txt` with the build output (AI-06: a warning when they differ, such as when the managed `robots.txt` of the host is on), then sends to IndexNow (`https://api.indexnow.org/indexnow`, 10,000 URLs per request at most) the URLs of the sitemaps that are new, that have another `lastmod`, or that left, of the host of the release only. A host with no sitemap before, a deployment with `--switch` (R85: the first deployment of the real host, only for the canonical host, with `--content-store`; it changes no date) and a deployment whose read of the live sitemaps fails send every URL of the sitemaps. Each call to the host and to IndexNow has a time limit of 10 seconds (`SEARCH_TIME_LIMIT`), and IndexNow comes after the cleanup of the object storage. The URLs that IndexNow did not take wait in `.cache/deploy/<worker>/indexnow-pending.json` of the machine, and the next deployment sends them first; a file that is not a list of URLs is never written over. That file is on one machine: a deployment from another machine does not send them. IndexNow gets nothing in a dry run, from a release that is not seen live, from a target marked `noindex`, or from a target whose host is not the canonical host. A failure is a warning: the release is live, and the result line does not change.
- A token of the deployment needs: edit the Workers and the object storage of the account, and edit the Worker routes of the zone. It lives in a private `.env` file of the machine, outside this repository.
- The deployment reaches the object storage through the REST API of Cloudflare with its token (`r2Storage()` of `apps/site/worker/r2.ts`, the port `AttachmentStorage` of the publishing logic): it lists the object storage page after page (1,000 names per page, with the cursor of the answer), uploads a key as the body of one `PUT` (an object shows only when its upload ended, so a key never names a part of a file; the API takes 300 MB at most per object) and deletes a name with `DELETE`. A message of a refusal has the status and the messages of the API, never the token.
- The account of the host needs its paid plan: a release has more than 20,000 files (R75).
- The zone features that can rewrite HTML must be off for the host (issue 118, URL-18). The edge removes the `ETag` of an HTML answer while such a feature is on, so a page never answers 304, and the obfuscation of email addresses changes the text of a note and adds a script. A Configuration Rule of the zone that serves the host names the host only and turns off: Email Address Obfuscation, Automatic HTTPS Rewrites, Server-side Excludes, Rocket Loader, Cloudflare Fonts, Zaraz and the automatic Web Analytics (RUM). "Replace insecure JavaScript libraries" has no rule setting, and it was the one that removed the tag on the preview host: it is off for the whole zone, so it is the one setting that changes for every host of that zone (accepted by the author for that zone). Measured on the preview host: a page has a weak tag with Brotli and a strong tag without compression, and answers 304 with compression. Check with `bun run urls check --base <address>` (its two checks of a file that did not change) and with a page that holds an email address, compared byte for byte with the build.

## The URL contract

The resolver (`packages/resolver/src/resolver.ts`) turns a requested path into an answer. It is a pure function: the handler of the site calls it, and the plain server and the Worker of the host are the two adapters of that handler (HOST-02). The shared table `fixtures/urls.json` states the answer of each kind of request on a site of fixture notes. It runs on the resolver alone (`packages/resolver/src/table.spec.ts`) and over HTTP against the plain server and against the Worker, after a real publication and a real build (`apps/site/src/urls-page.spec.ts`). A host runs it by its address with `bun run urls check` (the preview host with issue 32).

1. A path of the map is the answer, as requested, with its percent-encoding: a page (200), a file (200), an attachment. A variant of an image of the map (issue 87, `variantAt()`: `/-/attachments/<key>/w<width>-<generation>/<address name of the image>.webp`, for a JPEG, PNG or WebP of the map, the generation of the code, a width of `VARIANT_WIDTHS`) is the file `<key>-w<width>-<generation>.webp` of the attachment storage, as `image/webp`. The address holds the address of the image, so one lookup of the map finds it. The map does not say the width of an image, and a deployment can fail to make a variant: when the storage lacks the variant, the answer is the file of the image, with its own kind, kept one hour (`public, max-age=3600`), so a page never shows a broken image; when the storage lacks the image too, it is a failure of the release (500).
2. A path under `/-/` has no variant: the deployment record (`/-/deployment.json`, 200 with `no-store`, or "not found" when the release has none), a path of the map, the former Markdown path of a note that moved, as its old path was written (301 to the Markdown of the note, kept one hour, R66), the Markdown path of an unpublished note (410), or "not found" (URL-26).
3. Else the resolver reads the path in three readings, in this order, and the first one that finds a note wins (URL-03): `+` as a space, then `+` as itself, then `%2B` as a space too. A reading whose percent-encoding is not valid UTF-8 finds nothing.
4. In a reading, the text without a slash at its end, and then also without a `.md` suffix in any letter case, is looked for, in this order (URL-04):
    - a note or a folder whose text (the vault path without `.md`) has the same folded form: 301 to its canonical URL, kept one hour (`public, max-age=3600`). After a rename in letter case, a browser that kept the old redirect can loop between the two forms for that hour at most (R47). That covers another letter case, another Unicode form, `%20` for a space, a slash at the end and a `.md` suffix (URL-22). A folder with a published folder note (`Folder/Folder.md`) leads to that note, and a folder without one to its list (URL-16). A note and a folder with the same text: the note wins;
    - a former path of a note that moved, in the same folded form (the old vault path without `.md`): 301 to the note, kept one hour (`public, max-age=3600`, URL-06, URL-21, decision R66). A former path was the canonical URL of the note (business rule 1), so it wins over a file name and an alias of another note. A current address comes first: in each reading, a note or a folder whose text has the same folded form wins over a former path, also when a new note took the old path. A former path with the folded form of the text of an unpublished note is no redirect: the next steps of this list look for the text, and else it is gone (410, rule 6). A former path of several notes gives the "not found" page with those notes (rule 5), whatever note held it last;
    - an old path of the redirect list (issue 44, R79), in the same folded form: 301 to its target, kept one hour (`public, max-age=3600`). It wins over a file name and an alias, and over an address that would answer gone (rule 6);
    - a former folder (the folder of a former path of a published note), in the same folded form, when every published note with a former path directly in it is now in one folder: 301 to that folder (its folder note or its list), kept one hour (decision of the author R82). A former folder whose notes moved to two folders or more, or to the root, is no address; a current note or folder with that text wins, and so does an old path of the redirect list. A former folder whose text is the text of an unpublished note stays gone (410). A former folder wins over a file name, an alias and a former file name of another note;
    - a file name, when the text has no slash: 301 to the note, kept one hour (`public, max-age=3600`, URL-23);
    - an alias: 302 to the note, not kept (`no-store`, URL-24);
    - when no reading finds one of the above, a former file name of a note that moved, when the text has no slash: 301 to the note, kept one hour. It also wins over the file name of an unpublished note (410), because a published note had it (decision of the author R82).
5. A file name, an alias, a former path or a former file name of several notes gives the "not found" page with those notes (404, decision of the author, R47). A file name wins over the alias of another note. A former Markdown path of several notes names none of them. The decision R82 gives a former path of several notes to the note that held it last, with the time of each move in the manifest entry (point 9 of issue 105): decided, not built.
6. Only when no published note, folder or page has the path (none of the steps above finds it): an address of a note that the author unpublished is "gone" (410, URL-27, decision R64). The map holds the keys of these addresses (`goneKey()`), and the resolver hashes the forms of the request to look for them. A note that was unpublished and then came under a guard leaves the manifest at the next publication (a forced removal), so its addresses answer 404 (URL-28). That is its canonical path and its Markdown path as written, and in the readings and forms of rule 4 its text, its file name (when the text has no slash) and its aliases, with no redirect, and the same addresses of each of its former paths (R64, R66). A Markdown path under `/-/` has no variant. A name or an alias of several unpublished notes is gone too.
7. Then a query encoded into the path (`Note%3Fref%3Dsite`, RES-02): the text before the first `?` of a reading is looked for one time, by rule 4, and a redirect that it finds goes to its target with the encoded query as a real query (`?ref=site`), then the query of the request after a `&`. It comes after the gone addresses: a name with a question mark is a name, so an unpublished note `Why?` stays gone, and the text before the query is the address of an unpublished note (410) only when no published address and no row of the list has it: a live file name, a live alias or a row that an unpublished note shares wins. Then a prefix rule of the redirect list (RES-04): a path under an old folder, in the readings and forms of rule 4, leads to the target of the longest prefix that it starts with (301, kept one hour), with a query that is encoded into the path as a real query, as above. The folder itself is no address of the rule. A gone address and every exact address win over it, so a rule of a folder that is live again only leads a path under it that nothing else has. One request hashes a text one time for the gone part, the redirect list and the prefix rules, and hashes only the folders of the lengths of the prefix rules.
8. Everything else is "not found" (404). A name cut at a dot (URL-30) is not found, unless the redirect list names it (RES-01). A path with a bare percent sign (a `%` that two hex digits do not follow, `/100%+rye+bread`) is not found on the plain server and on the Worker.
9. A redirect keeps the query of the request, so that the parameters of analytics survive. A page with a query is the page (200, URL-12).
10. The folded form is the one of the publishing tool (`documentation/Canonical Form.md`, "The root names of the site"): the composed Unicode form, then small letters. A plan stops when two published paths have one folded form, so a folded text names one note or one folder.

A path with a bare percent sign never reaches the Worker on a real host: the edge of the host refuses it with 400 and its own short page (decision of the author R87, issue 119). The Worker cannot change that answer, and it is accepted. It is the one written exception to business rule 1: a few old URLs of the redirect list have this form and answer 400 after the switch. The new links of those notes encode the sign as `%25` and work. The case of the table gives that answer in `realHost` (`{ "status": 400 }`): `bun run urls check` on a host that is not on this machine (`isRealHost()`: not `localhost`, `127.*` or `[::1]`) expects 400 and fails on the not found page of the site, which would mean that the edge let the request through. The tests on the plain server and on the Worker still expect 404 with the page of the site.

Not done in this slice: `http://` to `https://` (URL-25) is a rule of the host (issues 21 and 32). The Markdown of a note page for `Accept: text/markdown` (URL-11) with issue 101.

`bun run first-request --base <address> (--floor-target <target file> | --floor <address>) [--paths <file>] [--requests <count>] [--parallel <count>] [--every <seconds>] [--out <file>]` (`scripts/first-request.ts`, issue 121, PERF-29) checks the first request of a new instance of the Worker against its budget (`FIRST_REQUEST_BUDGET` of `apps/site/src/budgets.ts`: the resolver map adds at most 60 ms to the time to the first byte at the 95th percentile, against a Worker with no map in the same run, 20 first requests at least on each side). With `--floor-target` it deploys a temporary floor Worker (`apps/site/worker/floor.ts`, one page of the host as its only static file) on the `workers.dev` name of the account of that target file, with the token of the deployment, asks both in turn, and deletes it at the end, also after a failure or a signal (Ctrl-C, SIGTERM, SIGHUP); the floor answers `X-Robots-Tag: noindex`, and the check stops when the page of the host that the floor copies does not answer 200; `--floor` takes the address of a floor that exists. Deploy the host just before a burst: a new floor has only new instances. Each request goes with curl on a new connection; the Worker marks the first answer of each instance with `Server-Timing: instance;desc=new` (`NEW_INSTANCE_TIMING`). Without `--every` it sends a burst (for right after a deployment): `--requests` requests on each side (60 by default), `--parallel` at a time on each side (4 by default); with `--every` one request at a time around that interval, which gives the share of the requests of a host with few readers that meet a new instance. The paths come from the sitemaps of the host, or from `--paths`. The last line is the summary as JSON (the host, the floor, and what the map adds at the 95th percentile, with the verdict); only the answers 200 are judged; the exit code is 1 when the budget breaks and when a side has too few first requests for a verdict. Run it on the preview host, with the map of the published notes, from a machine near the edge.

`bun scripts/measure-resolver-map.ts [--vault <folder> | --paths <file>] [--redirects <file>] [--former-paths <count>]` measures the resolver map of a vault as if every note of it were published (or of the vault paths of a file, one per line): its size, its size with gzip, the time to read it and the time of one resolution. With `--redirects` it adds a redirect list and also gives the size without it, the dropped rows, the time of the first request of a host (the read of the text, the check of its shape and one resolution, with no warm-up) and the time of a resolution of an old path. `--former-paths` gives every note that many invented former paths, each in another folder (`Former <n>/<vault path>`), and the output counts the part `former` of the map, its former folders too (issue 105, R82): a former path is never removed (business rule 1), so the map grows with every move, by about 260 bytes per former path on the fixture vault. It prints numbers only. The numbers of the invented corpus are in `documentation/research/2026-11-19-resolver-map.md`.

### The redirect list

The redirect list (issue 44, section 10.3 of the spec, R79, ADR 0013) holds the old addresses of the current site that no other rule finds: the former paths from before the first publication, names cut at a dot, old documentation, old generated notes. It is `redirects.json` at the root of the content store: private, because its rows name paths and titles of notes. The author writes it (a private script builds it from the reports of the search engines, the 404 data and the rename history of the vault) and commits it in the content store; the next deployment reads it. The publishing tool never reads or writes it. The public CI has none.

```json
{
    "version": 1,
    "redirects": [{ "from": "Old folder/Old name", "to": "/New+folder/New+name" }],
    "gone": ["Old folder/Old note"],
    "prefixes": [{ "from": "Old docs/", "to": "/Docs+hub" }]
}
```

- `from` is the old path decoded, as a vault path without `.md` and without a slash at its start, so one row covers every encoding, letter case, Unicode form, slash at the end and `.md` suffix (RES-06). A prefix ends with a slash; another old path never does. No empty part, never under `-/`, no `%` with two hexadecimal digits (a path that is still encoded), and no `.md` ending.
- `to` is a path of the site (the canonical path of a note, `/`, a generated page) or an `https://` address, with no fragment. An address on the host of the site (its origin as `URL` reads it: any letter case, with or without the port 443) is a path of the site: its path and its query.
- Each part is optional. The reader (`redirectListFrom()` of `packages/resolver/src/redirects.ts`) refuses another version, an unknown key (the message says "a key is not known" and never repeats it), a wrong row, two rows with one folded old path, two prefix rules with one folded prefix; the build then stops with the name of the file, the row and its part (`row 2 of redirects`), and no path.
- The build (`applyRedirectList()`, called by `apps/site/src/pages/-/resolver-map.json.ts`) puts the redirects and the prefix rules into the part `redirects` of the resolver map, by the key of their folded old path (`goneKey()`, as the gone part) with their target as text: `folded` for an old path, `prefixes` for an old folder with its slash, `prefixLengths`, the lengths of those folders, the longest first, `longest`, the length of the longest folded old path (a longer text of a request is never hashed), `temporary`, the keys whose target the build reached through an alias (they answer as an alias: 302, not kept, R47), and `counts`, what the build did with the rows (numbers only). Each gone row goes into the gone part, as a key. The build first reads every row, then follows each target as a request would be answered, in the order of the resolver (URL-05): a current note or folder or a former path of the release (a page or a file is the end, a redirect is followed), then a row of the list with that old path, then a file name, an alias or a former file name of the release, then a gone address (of the list, or of an unpublished note), then a prefix rule. A redirect of the release is no step. A loop is one row or one prefix rule of the list used twice; a chain uses at most every row and prefix rule of the list, plus two steps. The map keeps the canonical location where a target ends, with its query. Every old URL keeps working (R79): a row whose target is gone or leads to no page leads where the prefix rule over its own old path leads (the longest first), else to the hub of the parent folder of its old path when that folder is live, else to `/` (counted as "rows sent to a fallback"); only a row of the gone part of the list, which the author writes, answers 410 (decision 1 of the author: no 410 unless he writes "gone", else the nearest public note); a prefix rule is never dropped: when its target is gone, leads to no page or loops, it leads where the next shorter prefix rule over its folder leads, else to the hub of its parent folder when that folder is live, else to `/` (counted as "prefix rules sent to a fallback"). It drops a row whose old path a published note, a folder or a former path has (shadowed: the live address wins, business rule 1), and a row whose target loops. An unpublish or a takedown never blocks a build (business rule 16). It keeps and counts a prefix rule of a folder that is live again, and a row that hides a file name or an alias of a live note. Its warning gives each count that is not zero, and no path.
- The resolver map holds no old path of the list, only keys. The map is no address of the site either (`/-/resolver-map.json` answers 404 on every host), and a test checks that no file of the output holds an old path of the list.

### The URL parity test

`bun run urls parity --base <address> [--list <csv>]... [--sitemap <xml>]... [--urls <text>]... [--concurrency <n>] [--gate] [--report <file>]` (`apps/site/src/url-parity.ts`) asks a host for every URL that its sources know. The sources are private files of the author, read where they are:

- `--list`: the first redirect list (CSV with the columns `source_url_path`, `target_path` and `status_code`). A row of 200 must give a page; of 301 or 302, one redirect to its target; of 410, the gone page; of 404, the "not found" page; a row without a status code waits for a decision (OPEN-14). A canonical row of a report that shows paths decoded is asked in the form of its target, when both are one path decoded.
- `--sitemap`: a sitemap (each `<loc>`), `--urls`: one URL or path per line, `#` for a comment (a report, a crawl). Such a URL must work: 200, or one redirect to a page that answers 200.

Each option can come several times. A path of several sources, also in another encoding, is asked one time (in the form where it comes first), with the most precise expectation: two paths are one URL when they share their strict decoded form (`+` a space, `%2B` a `+`); a path with no `%` (a report that shows paths decoded) also has the form with `+` as itself. A URL whose sources say two things that cannot both hold is a `conflict`, and is not asked: a source says it must work and another that it is gone or not found, or two exact expectations (a page, a redirect, gone, not found) differ in kind, or two redirects lead to two paths. A page and a redirect of another form of it to that page both hold. Paths are compared decoded (RES-06): the three readings of the resolver, in the composed Unicode form, so `+`, `%20` and a space are one, and a literal `+` and a space of a decoded report are one too; the query is left aside, the letter case is not. One redirect is followed at most (URL-05); a target on another host of the author is not asked: the run counts it as ok. A 200 row of the list that answers with a page must have a first-level heading in its main part (RES-03). A redirect whose location is not the expected target still matches when the host leads the expected target there, in up to 3 redirects (the list can write a target in another letter case or encoding). Each URL gets a class: `ok`, `pending`, `not-found`, `gone`, `wrong-status`, `wrong-target`, `chain` (the target redirects again), `no-content`, `server-error`, `no-answer`, `conflict`. The command prints the count of each class by source, and no path: the URLs that are not `ok` go to the file of `--report` (JSON, a new file, opened so that it must not exist, outside the clone or in `.private/`), and to the standard error only with `--show-paths`. `--map <file>` prints the counts of the redirect list that the resolver map of a build holds ("the redirect list of the build: ..."), so the gate sees the prefix rules sent to a fallback and the rows that the build dropped. A report path inside the clone, outside `.private/`, is refused (code 2), and so is a file named `.private` itself; the place is compared after its links are followed, and a file in a folder that does not exist is refused too. A report file that exists is refused (code 2). `--concurrency` defaults to 8. It ends with the code 1 when a URL does not answer as expected, and with `--gate` also when a row waits for a decision (SW-04).

The tests of the builds write their output to `apps/site/.cache/`, which git ignores. The folder must be on the file system of the site: Astro moves files into the output folder, and a move to another file system fails.

To see a note on this machine: publish it into a copy of a content store with the command line program, build with `CONTENT_STORE=<copy> bun run build`, then `bun run serve --attachments <folder of the attachment storage>`.

    - The frozen lists (issue 40, decision R71): before each plan (Dry run, Publish, and the `plan` tool of its MCP server), the plugin asks the Dataview Serializer to refresh the lists of the notes of the plan that have a list to refresh, through its API `refreshNotes(paths)` (version 3.9.0 or later; `src/app/serializer.ts`). It waits first, at most 30 s, until the metadata cache of Obsidian holds the new `public_note`. A failed refresh fails nothing: the report of the run lists the notes that it wrote and the ones that it did not refresh, with the reason, and the run log names them. The Rust face has no limit for the length of a line.

A path that is not absolute deploys nothing either, by one rule of both faces (`isAbsolutePath`, `is_absolute_path`): on Unix a path that starts with `/`, on Windows a drive with its separator (`C:\`) or a network path (`\\server\share`), never `\foo` or `/foo`.

The plugin starts the deploy as the leader of a process group of its own and stops the group (SIGTERM, then SIGKILL after 5 seconds); the Rust program also starts the deploy in a process group of its own, and stops that group and each process of its tree (from `ps`, for a program that left the group) in the same way. Ctrl-C in a terminal reaches only the Rust program, because the deploy is in a group of its own. The handling of Ctrl-C starts when the deploy starts; before that, a Ctrl-C has the default of the system. While the program waits for the deploy (`deploy`, and the deploy after a push), a Ctrl-C stops the deploy with the programs that it started in the same way, and the deploy report says "the deploy was stopped by the author" (issue 126); a second Ctrl-C during the stop skips the wait of 5 seconds and kills them at once (KILL on Unix, `taskkill` at once on Windows), and the program still writes its report. A deploy that ends with the exit code 0 is read by its result, also when the stop came first (both faces). After the report, the program stops as Ctrl-C stops a program, so that a loop of the shell stops too: on Unix by the default action of SIGINT (a shell gives the exit code 130), on Windows with the exit code 130. A Ctrl-C after the deploy, before the end of the program, stops it in the same way at once. The deploys of the MCP server run in the background: there Ctrl-C stops the server, not the deploy. On Windows a crash of the program leaves the deploy running (its tree ignores Ctrl-C). On Windows both stop the tree with `taskkill /T /F`; the Rust program starts the deploy in a process group of its own there too (`CREATE_NEW_PROCESS_GROUP`), so a Ctrl-C reaches only the program, which stops the tree. In the plugin, "Stop the deploy" stops the deploy that runs in the same way; a deploy that waits then runs.

## Publishing logic and parity

- The commands of the Rust program, for now:
    - `status --vault <folder> --content-store <folder>` writes the publication queue: the lists `new`, `changed`, `toRemove` and `unchanged` with a count per list, `technicalUpdates` for the changed notes that the author did not edit, `missing` for the notes of `toRemove` whose file this device does not have and that no guard excludes, `unpublished` for the paths of the unpublished entries of the manifest, the exact paths that `takedown` takes, also of a note whose file this device does not have (issue 104), and `unpublishedUnderGuard` for the unpublished notes that a guard excludes, which the next publication removes (R64), `renamed` for the moves of the new lines of the rename journals, which the next publication applies, `movedEdited` for the moved notes whose text at the new path is not the published text (an edit after the rename, or another note at that path: their update waits for `--include`, R67), `pairings` for a published note that is missing and a candidate with the same source, which the author can confirm (R66), and `tooLarge` for the published notes that link to a file above the size limit of an attachment (100 MiB, issue 72), each with the file and its size: their update waits. It changes nothing.
    - `plan --vault <folder> --content-store <folder> [--include <vault path>]... [--hold <vault path>]... [--remove <vault path>]... | [--selection <file>]` computes a plan, stores it on the device and writes it with its id. Without a path, the plan holds the changed notes only, without the notes of `movedEdited`, which `--include` names. A note that was never published enters a plan only with `--include`. `--hold` leaves a changed note out. `--remove` unpublishes a published note. `--pair <from> <to>` confirms a pairing: a published note that is missing from this vault and the candidate that is that note now, also when its content differs (a rename outside Obsidian with an edit, PUB-96); the entry moves, the old path becomes a former path, and the candidate is published as an update unless `--hold` names it. Every plan applies the moves of the rename journals: they cannot be held. `--selection <file>` reads the lists from a JSON file in the place of the options (`{"include": [...], "hold": [...], "remove": [...], "pair": [{"from": ..., "to": ...}]}`, each list optional): a large first publication holds more paths than the system takes as arguments of one command. It changes nothing in the vault and in the content of the store, but it puts back what a publication that stopped halfway left in the copy. Its output also says `offline`: `true` when the content store could not be reached and the plan uses the last fetch, with a warning on the error output. Its list `tooLarge` names the notes that the plan holds because they link to a file above the size limit of an attachment, each with the file and its size.
    - `publish --vault <folder> --content-store <folder> --attachment-storage <folder> --plan <id> [--time <time>] [--device <name>]` applies one plan: the upload of the new attachments of its notes to the attachment storage, one commit with the cleaned notes, the manifest entries and `withdrawn.json` (the keys that the guards withdrew, issue 120), a push without force, the correction of the `public_note` property in the vault, then the deletion of every file of the attachment storage that no published note uses, and a new upload of every file that one uses and that the storage lost. It writes the publication report. Without `--time`, the program reads the clock one time. Without `--device`, it reads the name of the host. The name goes into the message of the commit, with the counts and the face.
    - `unpublish --vault <folder> --content-store <folder> --attachment-storage <folder> --path <vault path>... [--time <time>] [--device <name>]` unpublishes the named published notes in one step (PUB-80, R65): it makes the plan that removes them and holds every other changed note, stores it, and applies it as `publish` does (an unpublish that rule 10 of "The edits of the guards" refuses stores no plan, in both implementations), with one lock and one fetch: it needs the network, and it first puts back a publication that stopped halfway. Only the named notes leave, with the forced removals that every plan holds, and their addresses answer 410 after the next build. It writes the publication report.
    - `takedown --vault <folder> --content-store <folder> --attachment-storage <folder> --path <vault path>... [--time <time>] [--device <name>]` takes the named notes down at once, with no plan (PUB-81 to PUB-84, PUB-99, R65): each note leaves the content store with its manifest entry and its former paths, in one commit that is pushed, so every address of the note answers 404 once the deploy that the takedown starts is live, also the addresses of an unpublished note. Then the tool deletes the files of its attachment folder that no published note uses (the deploy, with `--takedown`, deletes them from the object storage of the host), and the `public_note` property leaves the notes (never in a folder of the deny list). A published or an unpublished note can be taken down; each path must be exactly the path of a manifest entry, and a path that is not stops the whole takedown, with a message that names the paths of the manifest in another letter case or Unicode form, or with the end `.md`. `--vault` is read only for the property: on a device with no copy of the vault, an empty folder works. A stale plan, a failed publication, a deny list entry that names no folder and a missing Starter Kit do not stop it; a lock, a copy that is behind (pull first) and a refused push do, and then nothing is taken down. It writes the takedown report (`takenDown`, `attachmentsDeleted`, `propertyRemoved`, `storageWarnings`, `warnings`), and ends with exit code 1 after the report when `storageWarnings` is not empty: a file that stays in the storage can still be public. A name of the storage that is not a key counts too, because it can mean that the folder is the wrong one. Each takedown first deletes the files of the storage that no published note uses, so a takedown that stopped after its push is finished by the next takedown or publication. After a takedown, the note is a candidate again: only `--include` publishes it again. A link to it in another note stays, as plain text.
    - What a takedown cannot do (PUB-86, PUB-85): copies in the caches of browsers and at crawlers cannot be recalled, and the text of the note stays in the history of the content store and of every clone of it (issue 103). The site changes when the deploy that the takedown starts is live, and that deploy deletes the files of the takedown from the object storage at once, also when its build or its deployment fails; the tool deletes the files of its own attachment folder.
    - `mcp --vault <folder> --content-store <folder> --attachment-storage <folder> [--osk-cli <program>] [--renames <folder>] [--device <name>] [the options of the deploy] [--no-deploy]` serves the MCP server of the tool over the standard input and output, one message of JSON per line, until the input ends (issue 41, TOOL-03). Its tools are the other commands, with the same names, the same output and the same refusals: `status`, `plan` (the arguments `include`, `hold`, `remove` and `pair`, as the selection file), `publish` (`plan`), `unpublish` and `takedown` (`paths`), `unlock`, `guards`, `deny`, `allow`, `ignore` and `unignore` (`path`), and `deploy` (`takedown`, `last`). A run takes the time of the clock, and its face is `mcp-server` in the commit message. An error is a tool result with `isError`; a report that names a failure is an `isError` result with two texts, the report and the failure. The failure names each note that was left out with its reason, or each file of the storage with its warning, because a client can cut the middle of a long error (Claude Code keeps the first and the last 5,000 characters); the commands write the same text to the error output. The places are checked at the start: a folder that does not exist stops the program before the first message. Add it to Claude Code with `claude mcp add vault-publish -- dsebastien-vault-publish mcp --vault <vault> --content-store <copy> --attachment-storage <folder>`.
    - `guards --vault <folder> --content-store <folder>` writes the guards (issue 42, R69): the deny list (`denyList`), the open proposals (`proposals`) and the edits of the guards since the last publication (`edits`). It reads no network, takes no lock, changes nothing, and stops while the lock of the device is taken, as `status` does. It does not stop on a deny list entry that names no folder, so an agent can read the deny list that stops every publication.
    - `deny`, `allow`, `ignore` and `unignore`, each with `--vault <folder> --content-store <folder> --path <path> [--time <time>] [--device <name>]`, edit the guards (GATE-40, R69). `deny` adds a folder to the deny list and `ignore` sets `publish_ignore: true` on a note: they apply at once when they take no manifest entry away (as the next publication counts them, with the moves of the rename journals) and, for `deny`, put no attachment of a published note under the guard; else they are stored as a proposal with the lists `removes` and `affects`. `allow` removes a folder from the deny list and `unignore` removes the property: they are always a proposal. Only the author confirms or rejects a proposal, in the publication center of the plugin. Each edit takes the lock of the device, fetches the content store (it needs the network and stops when the copy is behind), and writes its event into `edits.json` (and `configuration.json` for a `deny` that applies) in one commit that it pushes. It writes `{"edit": <event>}`. A `publish` or an `unpublish` of the program (both faces of the program are agent faces) stops when its plan has a forced removal, or a published note that would lose a file under a guard (`guardedAttachments`), that `--accept <path>` (or the key `accept` of the selection file) does not name (rule 10 of "The edits of the guards"). Name a path only when the author named that note; else the author publishes the plan in the publication center. The next plan shows every event since the last publication in its key `edits`, and `status` shows the open proposals in its key `proposals`. An edit by hand of `configuration.json` or of the property is not logged.
    - `unlock --content-store <folder>` removes the lock of the device that a publication left when it stopped halfway (a crash, a power cut), and writes `{"removed": true}` or `false`. Run it only when no publication runs. The next `plan`, `publish` or `takedown` puts the copy back from the run journal.
    - `deploy --content-store <folder> --attachment-storage <folder> [--site-code <folder>] [--deploy-target <file>] [--deploy-env-file <file>] [--bun <program>] [--deploy-timeout <minutes>] [--takedown | --last]` runs the deploy of the site again, with no publication (issue 32), and writes the deploy report; with no option it runs with `--takedown` while a takedown waits; `--last` starts no deploy and writes the last deploy report, `running` and `takedownWaits`. `publish`, `unpublish`, `takedown` and `mcp` take the same options of the deploy, and `--no-deploy`: see "The deploy after a push" in the section Plugin.
    - Exit codes: 0, and 1 for an error. `publish` and `unpublish` also end with 1 when the report names a note that was left out, and `takedown` when the attachment storage gave a warning. The report is then written first. The deploy after a push never changes the exit code; `deploy` ends with 1 when the deploy did not succeed.
    - `status`, `plan`, `publish` and `unpublish` read the rename journals of the folder `--renames <folder>`, by default those of every configuration folder of the vault (R66, R82). Each publication applies the new lines and writes `renames.json` in the content store: how many lines of each journal it read, so a line is applied one time. A deny list entry that names no folder stops every run, and the message names the new path of that folder when a line of a journal moved it (PUB-91). The commit message also counts the moves (`N moved`).
    - `--content-store` is the copy of the content store on this device: a git clone whose `origin` is the content store. The plans, the lock of the device and the run journal are stored in its git folder (`.git/vault-publish/plans/`, `lock`, `journal.json`): on the device, never in a commit, never in the vault. One publication runs at a time on a device: `publish` takes the lock, and `status` and `plan` stop while it is there.
    - `plan` and `publish` fetch the content store first and stop when the copy is behind it, with a message that says to pull (`git pull --ff-only origin main`): a copy that did not pull would keep a note under a guard live (issue 70). Without a network, `plan` uses the last fetch and `publish` stops. `status` reads no network: its key `behind` says how far the copy is behind at the last fetch, and the program then writes a warning on its error output, with exit code 0.
    - The copy must be the root of its own git repository, with an `origin`, and its last commit must hold `configuration.json`, else the program stops (R67): a wrong folder, or a clone of another repository, must never read as a content store with an empty deny list. A new content store gets its configuration in its first commit. `configuration.json`, `manifest/`, `renames.json` and `edits.json` in the copy must be the files of its last commit, else the program stops. So after an edit of the deny list by hand, commit `configuration.json` and push it before the next run: the message of the program says so. It proposes a push only when the push would change `configuration.json` alone and not remove it (it reads the difference with `origin/main`, not the names of the files in the commits), and it proposes to put back the manifest, which the tool alone writes. A publication stages and commits only the files that it wrote, also when a rule of the store ignores them.
    - `--attachment-storage` is the attachment folder of the machine: the tool writes the attachments of the published notes there, and the deploy uploads each one that a release uses and that the object storage of the host lacks, from it (`--attachments` of the deploy). The tool holds no key of the object storage (decision 1 of the comment of 2026-11-25 on issue 32, OPEN-12 of the spec). Its files are named by the SHA-256 of their bytes. The program does not check the folder first: a publication with no upload never needs it, a takedown only deletes from it, and a note whose upload fails is left out and reported.
    - When the commit fails or the push is refused (another device pushed first), nothing is published: the program takes its commit back and puts every file of the publication back as it was, deletes the uploads of the run that no published note uses, the copy is as it was before, and no property is written in the vault. The author then pulls (`git pull --ff-only origin main`) and makes a new plan: the tool never pulls by itself and never forces a push. A run that stops halfway is put back by the next `plan`, `publish` or `takedown`, after `unlock` (see "Failure cases" in `Canonical Form.md`).
    - Every git command of the tool reads paths as they are written (a note name can hold `[` or `*`) and converts no line end, whatever the settings of the machine say. The one exception is the comparison of the copy with its last commit, which converts line ends as the copy converts them, and also compares the bytes of each file by its hash, with no filter of git (a file with Windows line ends is the same file). The paths of a publication go to git on its standard input, so the number of notes of one publication has no limit of the system, and the folder of the copy can be a relative path.
    - A note is read from the vault only by its exact path: each part must be a name of the folder listing, with the same letter case, and a symbolic link is not a file of the vault. Each run lists each folder of the vault one time and keeps the listing until its end, so a scan takes a time that grows with the number of notes (issue 69). The kind of each part of a path is read again before the note is read.
- In TypeScript the edits of the guards are `guards`, `edit`, and the decisions of the author `confirmProposal` and `rejectProposal` (face `plugin` only) of `apps/plugin/src/publishing/tool.ts`, with the log in `edits.ts` (issue 42).
- In TypeScript the same operations are `status`, `plan`, `publish`, `unpublish` and `takedown` of `apps/plugin/src/publishing/tool.ts`; `deploy` is `runDeploy()` of `apps/plugin/src/publishing/deploy.ts`, which the controller of the publication center runs after a push and with the tool `deploy`. They take a device (`ports.ts`): a vault, a content store, an attachment storage and the local store of the device (the plans, the lock and the run journal). `unlock` removes the lock. Each operation asks the vault for a vault of its run (`forRun`), which keeps the folder listings of that run only: a device lives longer than a run, in Obsidian and in the tests. `publish`, `unpublish` and `takedown` also take the time of the run, the name of the device and the face. `node/device.ts` gives a device from three folders (the vault, the copy of the content store, the attachment storage), with the `git` program of the system.
- The size limit of an attachment is 100 MiB, in one constant per implementation: `MAX_ATTACHMENT_SIZE` of `apps/plugin/src/publishing/attachments.ts` and of `cli/src/attachments.rs` (decision of the author of 2026-11-26, issue 72). Change both together. The tool asks the size of a file before it reads it, and never reads a file above the limit: a note that links one is held (see "The attachments of a note" in `documentation/Canonical Form.md`). The port `Vault` gives the size (`size()`, `Vault::size`).
- Both implementations read the properties of a note as lines of text, with the rules of `documentation/Canonical Form.md`, and use no YAML library.
- TypeScript: `apps/plugin/src/publishing/`. Rust: `cli/src/`. The Rust program uses `clap` for its commands and `serde_json` for data. The feature `preserve_order` of `serde_json` stays off: the canonical form needs sorted keys.
- `documentation/Canonical Form.md` is the written canonical form. `fixtures/canonical/` holds its shared cases: `cases.json` (data), `properties.json` (the properties of a note), `links.json` (the links of a note), `images.json` (the size of an image), `queue.json` (scenarios of the publication queue), `mcp.json` (the messages of the MCP server of the tool, with a stand-in for the operations) and `deploy.json` (the command of the deploy after a push and the reading of its result).
- `parity/harness.ts` builds the Rust program with `cargo build --locked` and asks cargo where the program is. `parity/*.spec.ts` compare the bytes of both implementations.
- The random parity test (issue 112, "How it is tested" in `documentation/Canonical Form.md`): `parity/random/` holds the generator of the cases (`case.ts`), their run on both implementations and the comparison (`run.ts`), and the printer of a case as a shared queue scenario (`shared.ts`). The short run is `parity/random.spec.ts`, in `bun run test` and CI: seeds 1 to 200 when `CI` is set, 1 to 60 elsewhere. `bun run parity:random [--seed <n>] [--count <n>] [--parallel <n>] [--verbose]` is the long run (`scripts/random-parity.ts`): the cases of the seeds `seed` to `seed + count - 1` (by default 1,000 cases from a seed of the clock, which it prints), one line for each case where the two implementations differ, with its seed, and exit code 1 when one differs. `--verbose` adds what each side gave. `--seed <n> --print` writes the case as a scenario of `fixtures/canonical/queue.json`. A run works in `.cache/test-stores/` and removes its folders. Each case starts many git processes: on Windows, where a process costs much more time than on Linux, a run takes several times longer.
- A shared `takedown` or `unpublish` step can name its `face` (issue 112); the TypeScript runner then runs it from that face (the plugin by default), and the Rust runner refuses a face other than `command-line`. The printed random cases name the face `command-line` on each run, as the random run does.
- ESLint refuses an import of `obsidian` and of the plugin code in `apps/plugin/src/publishing/` (`no-restricted-imports`).
- The Rust program writes its output with one write and a flush. A reader that closed the pipe is not an error. Another failure of the write gives exit code 1 with a message. Exit codes: 0 for success, 1 for an error, 2 for wrong arguments.
