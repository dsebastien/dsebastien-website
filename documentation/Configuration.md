# Configuration

## TypeScript

`tsconfig.json` at the repository root. Maximum strictness, from the Obsidian plugin template of the author, plus `exactOptionalPropertyTypes`, `useUnknownInCatchVariables`, `noUncheckedSideEffectImports` and `forceConsistentCasingInFileNames`.

- `types` is pinned to `bun` and `node`, so that a missing type package is a hard error.
- `allowJs` is off: JavaScript files cannot skip the type check.
- `lib` includes `DOM` for now. Packages that run only on a server get their own configuration without it.
- `jsx` is not set. It is added with the first package that needs it.
- Packages and apps extend this file. An Astro app also extends the strictest Astro preset.
- The root project holds `scripts/`, `packages/`, `parity/`, `apps/plugin/` and the configuration files: `bun run tsc` checks them. The site has its own `tsconfig.json` and is not part of the root project: `bun run check` runs `astro check` on it, where a warning fails the run.
- In `apps/site/tsconfig.json` the root configuration comes after the Astro preset, so that the strictness of the root wins (`allowJs` stays off).

## Workspaces

The root `package.json` declares the Bun workspaces `apps/*` and `packages/*`. `apps/site` is the Astro site. `apps/plugin` is the Obsidian plugin. `packages/testing` is the test support (`@dsebastien-website/testing`): it has no build step, and its entry is its TypeScript source. The root package depends on it, so that the tests of the root (`parity/`, `scripts/`) can import it. The root `Cargo.toml` declares the Cargo workspace, with `cli` as its only member.

## Lint

ESLint (`eslint.config.ts`): the recommended rules of ESLint, the strict rules of typescript-eslint with type information, and the recommended rules of `eslint-plugin-astro` for Astro components. Every rule is an error, and the lint script adds `--max-warnings 0`. `eslint-config-prettier` switches off the rules that Prettier owns.

Rust: `cargo clippy` with every warning denied. The Cargo workspace denies the `all` and `pedantic` groups of clippy and forbids unsafe code. `rust-toolchain.toml` pins one exact version of the toolchain for the machines of the author and for CI (the workflow names the same version, and a guard test compares the two): with "stable", a new version of clippy brought a new rule and failed CI with no change of the code. A guard test checks the pin.

## Commits

`commitlint.config.ts`: Conventional Commits with a fixed list of scopes and a header of 100 characters at most.

`.gitconfig` at the root declares four config-based hooks (Git 2.54 or later). `bun run setup` includes that file in the configuration of the clone, one time per clone.

- `pre-commit` and `pre-merge-commit`: `bun scripts/private-files.ts` refuses a commit that holds a private file (see "Private files" below). It runs first.
- `pre-push`: `bun scripts/private-files.ts --pushed` refuses a push of a commit that holds a private file.
- `pre-commit`: `scripts/git-hooks/format-staged.sh` formats the staged files with Prettier and stages them again.
- `commit-msg`: commitlint refuses a message that breaks the convention.

## Private files

`scripts/private-files.ts` is the check that keeps private files out of this public repository. It cannot see the real vault, so its rules use structure:

1. No file of a folder named `.private`, `.content` or `.cache`, at any depth and in any letter case.
2. A vault file exists only in `fixtures/vault/`: a Markdown file (`.md`, `.markdown`, `.mdx`) that starts with a block of properties, a file of a folder named `.obsidian` or `.trash`, and a file that ends in `.canvas`, `.base` or `.excalidraw`.
3. Every file of `fixtures/vault/` is declared in `fixtures/catalog.json`.
4. No symbolic link.

What it cannot find outside the fixture vault: a note without properties, an attachment, and real text that someone pastes into a file. Care stays necessary.

It runs three times, and each run reads the files and the catalog from the place that it checks:

- Before a commit and before the commit of a merge: the index. A change of the work tree that is not staged does not count.
- Before a push: each commit that the push sends. A cherry-pick, a rebase and a commit from a clone without the hooks run no pre-commit hook, so the push is the last door of the machine. Only the last commit of each pushed branch is read, not the commits before it.
- In the tests (`scripts/private-files.spec.ts`): every file of the clone that git tracks or does not ignore. The test also checks that git ignores the private folders, and `.obsidian/` and `.trash/`, so that the fixture vault can be opened in Obsidian.

A clone where `bun run setup` did not run has no hook. CI then finds a private file only after the push.

A Markdown file with properties that is not a note (for example an issue template) needs an exception in the script. One exists (issue 41): a skill of this repository, `skills/<name>/SKILL.md` whose first property is `name: <name>`, for a name of the list `SKILLS` of the script, because the standard of the skills wants properties. The vault of the author holds many private skills in the same form, so a name that is not on the list, a deeper path, or another first line is refused.

## Fixtures and test stores

- `fixtures/` holds the fixture vault, its configuration and its catalog. `fixtures/README.md` has the rules.
- Prettier does not format `fixtures/vault/` (`.prettierignore`): the notes are test data, and their bytes must not change.
- `.gitattributes` gives every text file Unix line ends on every system. A Rust test checks it for the notes on Windows too, because the parity rule compares bytes.
- The test helpers make their folders in `.cache/test-stores/` of the clone, which git ignores.

## Corpus of full size

`bun run corpus` writes an invented vault of full size for prototypes and budget tests (`scripts/generate-corpus.ts`, with the generator in `scripts/corpus.ts`).

- Options: `--seed` (default 1, from 0 to 4,294,967,295), `--notes` (default 20,735, the number of public notes that the research counted) and `--out` (default `.cache/corpus/`). The vault is in the `vault/` folder of the output.
- The same seed and the same number of notes give the same files, byte for byte, on every machine. The generator reads no clock and no random source of the system, and it writes its images without a compression library. A test pins the digest of a small corpus.
- The numbers follow the public counts of `documentation/research/2026-11-17-current-state.md`. Tuned to the totals and checked by a test: the size of the notes (about 66 MB for 71 MB) and the number of links (about 154,000 for 155,000). Close to the counts: the shares of the note types, the notes with an image, with aliases, with a table, with a frozen list, with a code block and with a link to a heading, and the aliases that two notes share. The words are invented syllables.
- Four media notes in ten are stubs, with no text. No link goes to a heading of a stub.
- Name patterns: a dot, an ending like a file extension, an apostrophe, a character outside ASCII, an ampersand, a literal plus, a percent sign. No name holds a question mark, because Windows refuses it. No two notes share a file name, also when letter case is ignored.
- A corpus of full size is about 32,000 files. It is written in a few seconds.

Both corpus commands share the rules of their output folder (`scripts/output-folder.ts`):

- Inside the clone, the output goes below `.cache/`, `.content/` or `.private/` only: git ignores those folders, and the check of private files refuses every file of them. Another folder of the clone is refused, also when git ignores it.
- The output is never the clone, a folder that holds the clone, a folder that the command reads, a folder inside one, or a folder that holds one. Symbolic links are resolved before the comparison.
- A command writes over a folder only when the folder is empty or is its own earlier output: it holds the marker file of the command, and the marker names the command. Files that the user added to an earlier output are removed with it.
- A path that is a file is refused.
- The options are checked before the earlier output is removed.

## Published corpus

`bun run corpus:published --vault <folder> --list <file>` copies the files that the list names from a vault into `.cache/published/vault/`, with their vault paths (`scripts/export-published.ts`). The author runs it on his machines with the list of what Obsidian Publish serves today, so that prototypes and budget measurements use the real published notes (decision R30).

- The list: a file that ends in `.json` is the site cache of Obsidian Publish (a JSON object whose keys are the paths) or a JSON list. Every other file is text with one path per line. An empty list stops the command.
- The path of the vault and the list are inputs of the command. Neither is stored in this repository. The list of the author is in his private working files.
- The command never reads a file outside the vault. A path of the list that leaves the vault is not read, and a symbolic link that leads out of the vault is not followed.
- A file that is missing in the vault, that leaves the vault or that cannot be read is written to `missing.txt` of the output, and the command goes on.
- A file that the list names two times is copied and counted one time.
- The command never writes into the vault, and its output folder never touches the vault (see the rules above).
- Its marker file, `published.json`, holds the name of the command and three counts, and no path.
- The public CI never has the published corpus. Its tests use the fixture vault as the vault, with an invented list.

## CI

`.github/workflows/ci.yml` runs on each push to any branch.

- Job `checks`: dependency audit (level high, with one advisory ignored: the workflow file says which and why), type check, Astro check, lint, tests, format check, build of the site and of the plugin. The job has the Rust toolchain, because the parity tests build the Rust program.
- Job `rust`, on Linux and on Windows: format check, clippy, tests.
- Job `budgets`: the time budgets of the note page (`bun run budgets`), then the invented corpus (`bun run corpus`) and the budget of the first search on it (`bun run budgets:search`, R57, R63).

The public CI never sees the content store (BUILD-11 of the spec). It builds the empty site and, later, the site of the fixture vault.

## Container for local work

`Dockerfile` and `compose.yaml` at the root. `docker compose up` installs the packages and runs the dev server of the site on `http://localhost:4321`. `SITE_PORT` selects another port of the machine.

- The image holds Node and Bun only, in the versions of `.nvmrc` and of `packageManager`. A guard test fails when they differ.
- The source of the clone is mounted, so a change of a file shows at once. The packages live in two volumes, apart from the packages of the host.
- `.dockerignore` excludes everything: the image build gets no file of the clone, so no private file can enter an image.
- The port is published on the machine only (`127.0.0.1`).
- The container runs as the user `node` (id 1000), so that the files it writes into the clone have the owner of a normal Linux account.
- It is not an image for production. The plain server that serves the built site comes with the first slice (HOST-02 of the spec).
- CI does not start the container. It is checked by hand.

## Site

`apps/site/astro.config.ts`: Astro with Tailwind 4 through its Vite plugin. `src/styles/global.css` imports Tailwind. Prettier formats Astro components with `prettier-plugin-astro`.

- The variable `CONTENT_STORE` names the folder of a copy of the content store. The build reads the cleaned notes (`notes/`) as a content collection and the manifest (`manifest/`), and nothing else. It never reads the vault. Without the variable the site has no note: that is the state of the public CI, which never sees the content store.
- One file per page (`build.format` is `file`). The page of a note is `-/note/<id>.html`, where the id is the identity of the note in the manifest. That name is plain ASCII on every system and on every host, whatever the name of the note is.
- The build writes the resolver map to `-/resolver-map.json` (`resolverMapOf` of `packages/resolver`, called by `apps/site/src/site-files.ts`): `pages` (the file of the page of each canonical path: the home page, each published note, each folder without a folder note, and the page with every backlink of a note that has one), `files` (`/robots.txt` and the Markdown of each note, with their kind), `attachments` (the key in the attachment storage of each hashed path of an attachment that a page uses), `folded` (the canonical path of each note and each folder, by the folded form of its text), `names` and `aliases` (the canonical paths of the notes of each file name and each alias, by its folded form), `choices` (the file of the "not found" page of each list of several notes), `notFound` (the file of the "not found" page), and `gone` (the addresses of the notes that the author unpublished, apart from the rest: the file of the gone page, and as sets of keys the canonical path and the Markdown path, the folded text, the folded file name and the folded aliases of each one; a key is 32 hexadecimal digits of the SHA-256 of the text, `goneKey()`, so the map holds no title and no alias of such a note; with `longest`, the length of the longest text, so that a longer text of a request is never hashed; decision R64). The build reads only the path, the aliases and the former paths of an unpublished entry. Its part `former` holds the former paths of the published notes in clear: they were public URLs. The map is for the resolver only: the host must not serve it. The attachments are not in the output of the build: the host gives them from the attachment storage.
- The generated files live under `-/` (URL-08): `-/md/<id>.md` (the Markdown of a note: its cleaned note, URL-10), `-/folder/<id>.html` (the list of a folder without a folder note, URL-16), `-/choice/<id>.html` (the "not found" page of a name or an alias of several notes), `-/backlinks/<id>.html` (the page with every backlink of a note with more than 50 backlinks, at `/-/backlinks/<id>`, where the id is the identity of the note; `noindex, follow`, no canonical link). The id of a folder or of a list is 16 hexadecimal digits of the SHA-256 of its vault path, or of the vault paths of the list joined with line feeds. `404.html` is the "not found" page, `410.html` the gone page (NAV-19: it shows nothing of the removed note, and its search field starts empty), `500.html` the server error page (NAV-20: one file with its style inside it, no script, no font, in the mode of the system; the integration `selfContainedPages()` of `src/self-contained.ts` puts the style sheets into it after each build and stops the build when it still names another file of the release), `robots.txt` a first version that allows all (issue 54 writes the real one). The three error pages are `noindex, follow` and have no canonical link.
- Each page has a canonical link to its canonical URL on `https://notes.dsebastien.net` (`site` of `astro.config.ts`), so a URL with a query shows the same page with a clean canonical link (URL-12). The layout is `src/layouts/Page.astro`.
- An attachment has a hashed URL, `/-/attachments/<key>/<name>` (the first part of URL-15): the key of the file in the attachment storage, then its file name, percent-encoded. `attachmentPath` of `packages/resolver` makes it. The stable URL that follows the vault path comes with the slice of the URL contract.
- The page of a note shows an embed of an image as an image, with the width and the height of the manifest entry (an embed with `|300` or `|300x200` gives that size), lazy loaded. An embed of a video or of a sound gets the player of the browser. An embed of another file, and a link to a file, are a link to its hashed URL. A Markdown image is an embed whose alternative text is its text. The kind of a file comes from the end of its name.
- The build reads the properties of a note from its cleaned note (`apps/site/src/note-properties.ts`), with the YAML reader and the options of Astro but for its tag for dates: a date stays the text of the vault, so the panel and the title band show the day and the time that the vault writes, in no other time zone.
- A note page under its title band (issue 48, R59): the properties panel (every property of the note, by the display rules of the site of today; a link of a property is a link when its target is published), the text, and the backlinks (the notes that link to the note, the newest update first, each with the sentence around its links; 50 at most, the rest on the page of the backlinks). A note with 3 headings or more of levels 1 to 3 has an outline. On a wide screen the outline is in a left rail (from 1024 px) and the panel in a right rail (from 1280 px); on a smaller screen each is a folding block above the text. The panel is closed in the HTML; its script keeps the choice of the reader in the storage of the browser (key `properties`), and the key `p` opens and closes it.
- `packages/resolver` holds the URL functions (`canonicalPath`, `folderPath`, `markdownPath`, `attachmentPath`, `tagPath`, `backlinksPath`), the map of a site (`resolverMapOf`, `foldersOf`, `choicesOf`) and the resolver (`resolve`). The rules of the resolver are in the section "The URL contract" below. The first redirect list comes with issue 44. `errors.ts` gives the form of an error answer (`errorFormat()`) and its short Markdown text (`errorText()`, NAV-21). `handler.ts` gives the answer of a request (`siteHandler()`, with the port `Release` and its files `StoredFile`, `failureResponse()` and `ASSET_FOLDERS`): the URL contract over HTTP, with no knowledge of a host. `map.ts` checks the shape of a resolver map that a host reads (`resolverMapFrom()`, `RESOLVER_MAP_FILE`). Two adapters give the handler its files: the plain local server (`apps/site/server/serve.ts`, from folders) and the Worker of the host (`apps/site/worker/worker.ts`, from the static files of its Worker version through the binding `ASSETS`, and from the object storage through the binding `ATTACHMENTS`).
- `bun run site:fixture` publishes the invented notes of a copy of the fixture vault into a content store in `.cache/`, builds the site from it and serves it on `http://127.0.0.1:4322` (option `--port`). With `--sample` the vault also holds the budget sample (a long note with a long outline, a media note, a hub note with 489 backlinks), and the command prints the addresses of those three pages. Ctrl+C stops it and removes its folders. A second publication unpublishes one invented note that no note links to (`10 Garden/Bean trellis.md`), a takedown removes another one with the sound file that only it uses (`50 Field guide/Embeds/Embed of a sound.md`), and the command prints their addresses (the gone page, 410, and the "not found" page, 404) and the file of the server error page, which a working server never gives. Use it to look at the site with notes, attachments, folders and redirects; it never reads the real vault.
- `bun run urls build` publishes the invented notes of the URL table (`fixtures/urls.json`) from a copy of the fixture vault and builds their site into `.cache/url-table-site/` (`dist/` is the output for a host, `notes/` the cleaned notes; the command removes only an output of its own). `bun run urls check --base <address>` asks a host for every case of the table and for two files that did not change (304, URL-18), prints what has a finding and ends with the code 1 when there is one (SEAM-04, HOST-02). The tests run the same cases on the plain local server and on the Worker (`apps/site/src/urls-page.spec.ts`), so a preview host, a test host and a server of the exit path are all checked with one table.
- `bun run serve` starts the plain local server on `http://127.0.0.1:4322` (`apps/site/server/serve.ts`, options `--dist`, `--port` and `--attachments`). It answers through the resolver: 200 with the page or the file, a redirect with its `Location` and its `Cache-Control`, or 404 with the "not found" page (a redirect keeps the query of the request). A page and a file have an `ETag` of their size and their time, `Cache-Control: public, max-age=0, must-revalidate`, and answer 304 to a request whose `If-None-Match` names that tag (URL-18). A "not found" answer has `Cache-Control: no-store`. An address of an unpublished note answers 410 with the gone page, `no-store` too. Every error answer (404, 410, 500) has `Vary: Accept`, and its form follows `errorFormat()`: a path under `/-/md/`, or an `Accept` header that prefers `text/markdown`, gets the short Markdown text of `errorText()` with the same status (NAV-21); the 404 text of a name of several notes lists them. A page or a file that the resolver map names and that the output of the build lacks answers 500 with `no-store` (URL-33): the release is broken. With `--attachments <folder>` (the attachment storage), it gives each attachment of the resolver map from that folder, by its key: with its kind from the end of its name, a cache time of a year, no right to run a script (`Content-Security-Policy` with `sandbox`, but for a PDF, which the viewer of a browser refuses in a sandbox, and `nosniff` for every file), and the part that a range request asks for (206, or 416 for a range outside the file; several ranges get the whole file) (HOST-05). An attachment of the map that the folder lacks answers 500 with `no-store` too (URL-33). It also gives the files of the `_astro/` folder of the output (the style sheets), from a list that it reads one time at its start; a file of that list that is gone answers 500. Every 500 is the server error page, which the server reads at its start (so a release that lost it still gives it), with no detail of the failure (NAV-20), also for a failure of the server itself; a build without that page gives the short text as plain text. The file of a response comes from the resolver map or from that list, never from the request. It is not a server for production.
- The search (issue 51, R63): the page `/-/search` (`-/search.html`, `noindex, follow`) runs `src/search/search-page.ts`. The build writes the title index to `-/search/titles.json` (the keys of its parts) and `-/search/titles/<key in hexadecimal>.json` (the parts, from `src/pages/-/search/titles`), and the integration `searchIndex()` (`src/search/search-index.ts`) writes the full-text index of the note pages with Pagefind to `-/search/pagefind/` after each build. The plain server gives the files of `-/search/` as it gives the files of `_astro/`. The dev server (`bun run dev`) has no full-text index, because the integration runs after a build only: on it the full text of the search page says that it could not load; build the site and serve it to try the search. `bun run budgets:search [--vault <folder>]` builds both indexes of a vault (the invented corpus by default) and fails when one search loads more than 350 KB (R63: the keys and every part of the title index that the letters of the query load, and the full text of the query with 10 results); it also reports the session of a reader who stops after each letter. It prints numbers only. The numbers are in `documentation/research/2026-11-22-search-index.md`.
- The build stops when the content store cannot be trusted: `CONTENT_STORE` names no folder, a file of the manifest is not an entry, the id of an entry is not 16 hexadecimal digits, or two entries have the same path.
- The markup of a note comes from the Markdown renderer of Astro for now. The slice of the rendering replaces it after the adopt check of issue 12.

## Deployment

A release goes to the host from the machine that publishes, never from the public CI (BUILD-02, BUILD-11, R76). The names of the host (the account, the Worker, the bucket, the host name, the zone) are in a private target file, never in this repository.

- `bun run deploy --target <file> --content-store <folder>` builds the site from the copy of the content store on this machine (`CONTENT_STORE`: the build reads it and never writes it) and deploys it. `--dist <folder>` deploys an output that is built already. The command refuses a folder that is not the output of a build (no resolver map, `checkOutput()`): the whole folder goes to the host. `--dry-run` checks the bundle with wrangler and uploads nothing.
- The target file is JSON: `accountId`, `worker`, `bucket`, `host`, `zone`, `noindex` (`targetFrom()` of `apps/site/worker/deployment.ts` refuses a wrong or unknown field). The host is always a route of `zone` (`<host>/*`): a custom hostname of that zone (Cloudflare for SaaS), or a name of the zone with a proxied DNS record. Never a custom domain: wrangler replaces the DNS record of a custom domain without a question when it runs with no terminal, so a wrong host would take over a live name.
- The command writes the wrangler configuration into `.cache/deploy/<worker>/wrangler.json` (`workerConfiguration()`: the static files give a file only by its exact name, the Worker runs first for every path but `/_astro/*` and `/-/search/*`, the binding `ASSETS`, the binding `ATTACHMENTS` to the bucket, no `workers.dev` address and no preview address), and the whole `_headers` file into the output, over any file of that name (`headersFile()`). Then it runs `wrangler deploy` (the version in `apps/site/package.json`), which reads the token from `CLOUDFLARE_API_TOKEN`.
- A preview host (`noindex: true`, IDX-26): the Worker sets `X-Robots-Tag: noindex` on every answer (its variable `NOINDEX`), errors and 304 included, and the `_headers` file sets it on every static file, which covers the files that the host gives without the Worker (`/_astro/`, `/-/search/`).
- A token of the deployment needs: edit the Workers and the object storage of the account, and edit the Worker routes of the zone. It lives in the secret storage of the machine.
- The account of the host needs its paid plan: a release has more than 20,000 files (R75).
- The zone features that can rewrite HTML must be off for the host (issue 118, URL-18). While one of them is on, the edge removes the `ETag` of every HTML answer, so a page never answers 304, and the obfuscation of email addresses changes the text of a note and adds a script. A Configuration Rule of the zone that serves the host, for the host name only, turns off: Email Address Obfuscation, Automatic HTTPS Rewrites, Server-side Excludes, Rocket Loader, Cloudflare Fonts, Zaraz and the automatic Web Analytics (RUM). "Replace insecure JavaScript libraries" has no rule setting: it must be off for the whole zone, and it was the one that removed the tag on the preview host. Check with `bun run urls check --base <address>` (its two checks of a file that did not change) and with a page that holds an email address, compared byte for byte with the build.

## The URL contract

The resolver (`packages/resolver/src/resolver.ts`) turns a requested path into an answer. It is a pure function: the handler of the site calls it, and the plain server and the Worker of the host are the two adapters of that handler (HOST-02). The shared table `fixtures/urls.json` states the answer of each kind of request on a site of fixture notes. It runs on the resolver alone (`packages/resolver/src/table.spec.ts`) and over HTTP against the plain server and against the Worker, after a real publication and a real build (`apps/site/src/urls-page.spec.ts`). A host runs it by its address with `bun run urls check` (the preview host with issue 32).

1. A path of the map is the answer, as requested, with its percent-encoding: a page (200), a file (200), an attachment.
2. A path under `/-/` has no variant: it is a path of the map, the former Markdown path of a note that moved, as its old path was written (301 to the Markdown of the note, kept one hour, R66), the Markdown path of an unpublished note (410), or "not found" (URL-26).
3. Else the resolver reads the path in three readings, in this order, and the first one that finds a note wins (URL-03): `+` as a space, then `+` as itself, then `%2B` as a space too. A reading whose percent-encoding is not valid UTF-8 finds nothing.
4. In a reading, the text without a slash at its end, and then also without a `.md` suffix in any letter case, is looked for, in this order (URL-04):
    - a note or a folder whose text (the vault path without `.md`) has the same folded form: 301 to its canonical URL, kept one hour (`public, max-age=3600`). After a rename in letter case, a browser that kept the old redirect can loop between the two forms for that hour at most (R47). That covers another letter case, another Unicode form, `%20` for a space, a slash at the end and a `.md` suffix (URL-22). A folder with a published folder note (`Folder/Folder.md`) leads to that note, and a folder without one to its list (URL-16). A note and a folder with the same text: the note wins;
    - a former path of a note that moved, in the same folded form (the old vault path without `.md`): 301 to the note, kept one hour (`public, max-age=3600`, URL-06, URL-21, decision R66). A former path was the canonical URL of the note (business rule 1), so it wins over a file name and an alias of another note. The last owner of an address wins: a current path or folder wins over it, also when a new note took the old path, and so does the path of an unpublished note that took it (410);
    - a file name, when the text has no slash: 301 to the note, kept one hour (`public, max-age=3600`, URL-23);
    - an alias: 302 to the note, not kept (`no-store`, URL-24);
    - when no reading finds one of the above, a former file name of a note that moved, when the text has no slash: 301 to the note, kept one hour.
5. A file name, an alias, a former path or a former file name of several notes gives the "not found" page with those notes (404, decision of the author, R47). A file name wins over the alias of another note. A former Markdown path of several notes names none of them.
6. Only when no published note, folder or page has the path (none of the steps above finds it): an address of a note that the author unpublished is "gone" (410, URL-27, decision R64). The map holds the keys of these addresses (`goneKey()`), and the resolver hashes the forms of the request to look for them. A note that was unpublished and then came under a guard leaves the manifest at the next publication (a forced removal), so its addresses answer 404 (URL-28). That is its canonical path and its Markdown path as written, and in the readings and forms of rule 4 its text, its file name (when the text has no slash) and its aliases, with no redirect, and the same addresses of each of its former paths (R64, R66). A Markdown path under `/-/` has no variant. A name or an alias of several unpublished notes is gone too.
7. Everything else is "not found" (404).
8. A redirect keeps the query of the request, so that the parameters of analytics survive. A page with a query is the page (200, URL-12).
9. The folded form is the one of the publishing tool (`documentation/Canonical Form.md`, "The root names of the site"): the composed Unicode form, then small letters. A plan stops when two published paths have one folded form, so a folded text names one note or one folder.

Not done in this slice: `http://` to `https://` (URL-25) is a rule of the host (issues 21 and 32). The folder of a former path is no address: its list page answers 404 when its notes moved. A name cut at a dot and a query encoded into the path (RES-01, RES-02) with issue 44, and the Markdown of a note page for `Accept: text/markdown` (URL-11) with issue 101.

`bun scripts/measure-resolver-map.ts [--vault <folder>]` measures the resolver map of a vault as if every note of it were published: its size, its size with gzip, the time to read it and the time of one resolution. It prints numbers only. The numbers of the invented corpus are in `documentation/research/2026-11-19-resolver-map.md`.

The tests of the builds write their output to `apps/site/.cache/`, which git ignores. The folder must be on the file system of the site: Astro moves files into the output folder, and a move to another file system fails.

To see a note on this machine: publish it into a copy of a content store with the command line program, build with `CONTENT_STORE=<copy> bun run build`, then `bun run serve --attachments <folder of the attachment storage>`.

## Plugin

`apps/plugin`, from the Obsidian plugin template of the author. Only what the skeleton needs was taken: the entry (`src/main.ts`), the plugin class (`src/app/plugin.ts`), the manifest and the build script. The release scripts and the lint rules of the plugin catalog are not taken yet.

- `manifest.json`: the id is `dsebastien-vault-publish`, the name of the Rust program too (TOOL-14). The plugin is for desktop only.

The folder must hold `.obsidian`, else the command stops and makes nothing. The path is read from the environment only, and it is never stored here.
- Use a test vault for `VAULT_PUBLISH_DEV_VAULT`, never the real vault, while the plugin is young. The plugin template reads `OBSIDIAN_VAULT_LOCATION`, which names the real vault on the machines of the author: this script does not read it, on purpose.
- The plugin records each rename that Obsidian reports in the rename journal of its device (PUB-60, decision R66): one line per renamed note or folder, appended to `<configuration folder>/plugins/dsebastien-vault-publish/renames/<16 hexadecimal digits>.jsonl` (`src/app/rename-journal.ts`). The name of the journal is made one time per device and kept in the local storage of Obsidian. A write that fails shows a notice: the move then shows as a pairing at the next publication. Limits:

Git must not convert the line ends of the journals (`.gitattributes` with `eol=lf`, as this vault has): the read marker hashes their bytes, and a converted journal reads as edited, so its new lines are not applied. Check it for another synchronization, such as Obsidian Sync, which can copy only some files of a plugin. A journal that does not arrive loses no note: its moves show as pairings.

    - The plugin is for desktop only: a rename on a phone writes no line, and shows as a pairing (or as a missing note and a candidate, when the note was also edited).

- The publication center (issue 39, decision R67): the command "Open publication center" (and the icon of the ribbon) opens a tab in the main area.
    - The settings of a device are in the settings tab of the plugin: the folder of the copy of the content store, the folder of the attachment storage, and the git program when Obsidian does not find `git` (it can start with another path of the system than a terminal). They are absolute paths, kept in the local storage of Obsidian (`src/app/settings.ts`), never in `data.json`: they never travel with the vault. A missing setting stops every check with a message that names it.

The defaults: a changed note is ticked, a candidate, a note that is missing from this vault and a moved note whose text is not the published text (`movedEdited`, R67) are not, a forced removal is ticked and locked, the technical updates have one check box (PUB-24). The ticks stay after a publication; a check drops the ticks of the notes that left their lists. The lists are virtual: only the visible rows exist in the page, and the view renders one time per frame. Each row has a check box, its path (Enter opens the note) and its menu (from the keyboard, the menu opens at its button) as stops of Tab, and a render gives the focus back to the element that had it. A file name is isolated from the text around it, so a right-to-left mark never reorders another name.

A click makes the plan again from the vault and publishes it only when it is that plan; else nothing is published and the view shows the new plan. A new note that changed after the check (another note can have its path) stops the publication too, and the lists are checked again. The notice "publication started" comes when the plan is the plan of the label. "Dry run" shows the plan and writes nothing into the vault and into the content of the store; as `plan`, it stores the plan record on the device and puts back a publication that stopped halfway. A publication, a takedown and a pull run in the background: the author can close the tab and write, and a notice gives the end. One activity runs at a time: another one is refused with a message, but a takedown waits for the end of the current one and then runs; after a run that changed the copy, or when a note changed since the check, it checks again first, so it finds the note where the content store has it; a check that fails never stops it (PUB-99): it then uses the last check, and it stops only when the note moved since its dialog named its path. A note whose move waits for the next publication is taken down at its old path, which the dialog names. A new note that changed after the check loses its tick when it stops a publication. The report stays until the author closes it, with the live addresses of the published and updated notes. The run log keeps the last 200 lines of the session.
    - A check runs when the command, the icon of the ribbon or the status bar opens the view, on "Refresh", on the command "Check for changes", and after each publication, takedown, pull and unlock; never at the start of Obsidian, also when Obsidian restores the view. It fetches the content store first when the network allows it, with the lock of the device. When the copy is behind, the view shows a Pull button: it runs `git pull --ff-only origin main` in the copy (`pullContentStore` of `node/device.ts`) with the lock of the device, refuses while another run holds it or while a publication that stopped before its push left its run journal (a journal of a publication that stopped after its push leaves a clean copy, which can pull), then checks again. The publish button waits for the pull.
    - A run that stopped halfway (a crash, Obsidian closed during a publication) leaves the lock of the device, and every check stops with its message. The command "Remove the lock of this device, after a run that stopped" and a button under the message remove it after a confirmation that shows the message of the lock. The tool does not check whether a run of another face still holds it: remove it only when none runs. The next dry run, publication or takedown puts the copy back.
    - The frozen lists (issue 40, decision R71): before each plan (Dry run, Publish, and the `plan` tool of its MCP server), the plugin asks the Dataview Serializer to refresh the lists of the notes of the plan that have a list to refresh, through its API `refreshNotes(paths)` (version 3.9.0 or later; `src/app/serializer.ts`). When the refresh wrote a note, the plan is computed again, so the plan holds the refreshed text. The writes of the refresh are no edit for the view, like the write of the state property: one event of each note that the refresh wrote is its write, and any other event during the refresh is an edit. A path that Obsidian changes (`normalizePath`, issue 110) is not asked. The plugin waits at most 10 minutes for the serializer, and a refresh that still runs then makes the next plans publish the lists as saved until it ends. A note that the serializer did not refresh (the plugin is off or too old, Dataview is not loaded or its index is not ready yet, the note has `dataview_serializer_ignore`, a query failed or kept its old output) is published with its lists as they are in the note now, maybe not refreshed: the dry run panel lists it under "Lists not refreshed" with the reason, and the run log names it. The notes with a live Dataview or Bases block are listed too: the page does not show such a block, and the publication report warns. The command line program refreshes nothing and prints a warning. A check by hand needs Dataview and the Dataview Serializer in the test vault: copy their folders from `.obsidian/plugins/` of a vault that has them.
    - The status bar item shows the state of the open note at the last check, with an icon and a text, and "(edited since the check)" when the note changed after it (the edits count once the layout of Obsidian is ready; the write of the state property by a run of the plugin is no edit). A note in no list is under a guard, or "not checked yet" when it changed after the check. A click opens the view on that note.
    - Other commands: "Unpublish the open note with the next publication", "Take down the open note now" (with the dialog of a takedown), "Copy the live address of the open note", "Remove the lock of this device, after a run that stopped", and "Show the measures of the publication center".
    - The plugin reads the vault and runs git through Node (`node/device.ts`, the device of the tests and of the parity harness), so it is for desktop only.
- The MCP server of the plugin (issue 41, TOOL-03, decision R68): the tools of the `mcp` command of the Rust program, over HTTP at `http://127.0.0.1:<port>/mcp` (`src/app/mcp-server.ts`; the messages are `src/publishing/mcp.ts`, the tools `src/publishing/mcp-tools.json`).
    - It starts when the plugin loads, on port 27126 by default, and stops when the plugin unloads. The settings tab turns it off, changes the port (Apply restarts it) and shows its state. A port that another program holds, or Vault Publish in another vault (a test vault and the real vault both start on 27126 by default), gives a notice: the rest of the plugin works. Give each vault its own port.
    - A key is always required: `Authorization: Bearer <key>`. The first start makes it (32 random bytes in base64url) and keeps it in the secret storage of Obsidian on that device (`dsebastien-vault-publish-mcp-key`), never in `data.json` or in the vault. The settings tab copies it, makes a new one, and copies the command for Claude Code: `claude mcp add --scope local --transport http vault-publish http://127.0.0.1:<port>/mcp --header "Authorization: Bearer <key>"`. Where the key can leak: Claude Code keeps it as plain text in `~/.claude.json` (the scope `local` keeps it out of a `.mcp.json` of the vault); on Linux with no keyring, Obsidian keeps its secrets without encryption and says so; and another program on this computer can listen on the port while Obsidian is closed, and get the key from a client that connects. The risk is small on a computer with one user. Make a new key in the settings tab when in doubt.
    - It listens on 127.0.0.1 only and refuses a request with an `Origin` header (a web page), a `Host` that is not `127.0.0.1:<port>` (DNS rebinding; `localhost` is refused too, because a client that asks it can reach another program on `[::1]` at the same port and give it the key), a `Content-Type` that is not `application/json` (415), a body larger than 1 MiB (413), and an unknown `MCP-Protocol-Version` (400). A body that does not parse gets a JSON-RPC parse error. A POST gets one JSON answer, with no session; a GET gets 405 (no stream of events), and a notification gets 202. A batch of messages gets "Invalid Request": the version 2025-06-18 of the protocol removed batches, and Claude Code sends none (a client of the version 2025-03-26 that sends one is refused). A number id must be a whole number that a double holds exactly, as in the Rust face. The answer comes when the run ends: a client on Node `fetch` stops waiting for the headers after 5 minutes (Claude Code runs on Bun and waits), so a very long first publication can lose its answer there. The Rust face has no limit for the length of a line.
    - Each call goes through the controller of the publication center (`PublicationCenter.serve`): it waits for the end of the current activity, so one run at a time holds the copy, and an action of the author waits for a call of `status` or `plan`, which change nothing that the view shows (a plan can put back a publication that stopped halfway; `status` refuses to read the copy before that). Such a call gives no notice and leaves the error of the view, but for its own failure. The run log, the report and the error of the view show what the agent did, and the notice at the end of a run shows the result of the run, not the check after it (`outcome` of the state). A publication, an unpublish, a takedown and an unlock of an agent give the notice at the end of a run and check again in the same activity, so no other call comes between them; that check keeps the marks of the new notes, of the moved notes whose text changed and of the ticked notes, so a publication of the view still stops on a note that changed before it. A run of the agent has the face `mcp-server`.

## Publishing logic and parity

- The commands of the Rust program, for now:
    - `status --vault <folder> --content-store <folder>` writes the publication queue: the lists `new`, `changed`, `toRemove` and `unchanged` with a count per list, `technicalUpdates` for the changed notes that the author did not edit, `missing` for the notes of `toRemove` whose file this device does not have and that no guard excludes, and `unpublishedUnderGuard` for the unpublished notes that a guard excludes, which the next publication removes (R64), `renamed` for the moves of the new lines of the rename journals, which the next publication applies, `movedEdited` for the moved notes whose text at the new path is not the published text (an edit after the rename, or another note at that path: their update waits for `--include`, R67), and `pairings` for a published note that is missing and a candidate with the same source, which the author can confirm (R66). It changes nothing.
    - `plan --vault <folder> --content-store <folder> [--include <vault path>]... [--hold <vault path>]... [--remove <vault path>]... | [--selection <file>]` computes a plan, stores it on the device and writes it with its id. Without a path, the plan holds the changed notes only, without the notes of `movedEdited`, which `--include` names. A note that was never published enters a plan only with `--include`. `--hold` leaves a changed note out. `--remove` unpublishes a published note. `--pair <from> <to>` confirms a pairing: a published note that is missing from this vault and the candidate that is that note now, also when its content differs (a rename outside Obsidian with an edit, PUB-96); the entry moves, the old path becomes a former path, and the candidate is published as an update unless `--hold` names it. Every plan applies the moves of the rename journals: they cannot be held. `--selection <file>` reads the lists from a JSON file in the place of the options (`{"include": [...], "hold": [...], "remove": [...], "pair": [{"from": ..., "to": ...}]}`, each list optional): a large first publication holds more paths than the system takes as arguments of one command. It changes nothing in the vault and in the content of the store, but it puts back what a publication that stopped halfway left in the copy. Its output also says `offline`: `true` when the content store could not be reached and the plan uses the last fetch, with a warning on the error output.
    - `publish --vault <folder> --content-store <folder> --attachment-storage <folder> --plan <id> [--time <time>] [--device <name>]` applies one plan: the upload of the new attachments of its notes to the attachment storage, one commit with the cleaned notes and the manifest entries, a push without force, the correction of the `public_note` property in the vault, then the deletion of every file of the attachment storage that no published note uses, and a new upload of every file that one uses and that the storage lost. It writes the publication report. Without `--time`, the program reads the clock one time. Without `--device`, it reads the name of the host. The name goes into the message of the commit, with the counts and the face.
    - `unpublish --vault <folder> --content-store <folder> --attachment-storage <folder> --path <vault path>... [--time <time>] [--device <name>]` unpublishes the named published notes in one step (PUB-80, R65): it makes the plan that removes them and holds every other changed note, stores it, and applies it as `publish` does, with one lock and one fetch: it needs the network, and it first puts back a publication that stopped halfway. Only the named notes leave, with the forced removals that every plan holds, and their addresses answer 410 after the next build. It writes the publication report.
    - `takedown --vault <folder> --content-store <folder> --attachment-storage <folder> --path <vault path>... [--time <time>] [--device <name>]` takes the named notes down at once, with no plan (PUB-81 to PUB-84, PUB-99, R65): each note leaves the content store with its manifest entry and its former paths, in one commit that is pushed, so every address of the note answers 404 after the next build, also the addresses of an unpublished note. Then the files of the attachment storage that no published note uses are deleted, and the `public_note` property leaves the notes (never in a folder of the deny list). A published or an unpublished note can be taken down; each path must be exactly the path of a manifest entry, and a path that is not stops the whole takedown, with a message that names the paths of the manifest in another letter case or Unicode form, or with the end `.md`. `--vault` is read only for the property: on a device with no copy of the vault, an empty folder works. A stale plan, a failed publication, a deny list entry that names no folder and a missing Starter Kit do not stop it; a lock, a copy that is behind (pull first) and a refused push do, and then nothing is taken down. It writes the takedown report (`takenDown`, `attachmentsDeleted`, `propertyRemoved`, `storageWarnings`, `warnings`), and ends with exit code 1 after the report when `storageWarnings` is not empty: a file that stays in the storage can still be public. A name of the storage that is not a key counts too, because it can mean that the folder is the wrong one. Each takedown first deletes the files of the storage that no published note uses, so a takedown that stopped after its push is finished by the next takedown or publication. After a takedown, the note is a candidate again: only `--include` publishes it again. A link to it in another note stays, as plain text.
    - What a takedown cannot do (PUB-86, PUB-85): copies in the caches of browsers and at crawlers cannot be recalled, and the text of the note stays in the history of the content store and of every clone of it (issue 103). The site changes only after the next build of the content store.
    - `mcp --vault <folder> --content-store <folder> --attachment-storage <folder> [--osk-cli <program>] [--renames <folder>] [--device <name>]` serves the MCP server of the tool over the standard input and output, one message of JSON per line, until the input ends (issue 41, TOOL-03). Its tools are the other commands, with the same names, the same output and the same refusals: `status`, `plan` (the arguments `include`, `hold`, `remove` and `pair`, as the selection file), `publish` (`plan`), `unpublish` and `takedown` (`paths`), `unlock`, `guards`, and `deny`, `allow`, `ignore` and `unignore` (`path`). A run takes the time of the clock, and its face is `mcp-server` in the commit message. An error is a tool result with `isError`; a report that names a failure is an `isError` result with two texts, the report and the failure. The failure names each note that was left out with its reason, or each file of the storage with its warning, because a client can cut the middle of a long error (Claude Code keeps the first and the last 5,000 characters); the commands write the same text to the error output. The places are checked at the start: a folder that does not exist stops the program before the first message. Add it to Claude Code with `claude mcp add vault-publish -- dsebastien-vault-publish mcp --vault <vault> --content-store <copy> --attachment-storage <folder>`.
    - `guards --vault <folder> --content-store <folder>` writes the guards (issue 42, R69): the deny list (`denyList`), the open proposals (`proposals`) and the edits of the guards since the last publication (`edits`). It reads no network, takes no lock, changes nothing, and stops while the lock of the device is taken, as `status` does. It does not stop on a deny list entry that names no folder, so an agent can read the deny list that stops every publication.
    - `deny`, `allow`, `ignore` and `unignore`, each with `--vault <folder> --content-store <folder> --path <path> [--time <time>] [--device <name>]`, edit the guards (GATE-40, R69). `deny` adds a folder to the deny list and `ignore` sets `publish_ignore: true` on a note: they apply at once when they take no manifest entry away (as the next publication counts them, with the moves of the rename journals) and, for `deny`, put no attachment of a published note under the guard; else they are stored as a proposal with the lists `removes` and `affects`. `allow` removes a folder from the deny list and `unignore` removes the property: they are always a proposal. Only the author confirms or rejects a proposal, in the publication center of the plugin. Each edit takes the lock of the device, fetches the content store (it needs the network and stops when the copy is behind), and writes its event into `edits.json` (and `configuration.json` for a `deny` that applies) in one commit that it pushes. It writes `{"edit": <event>}`. A `publish` or an `unpublish` of the program (both faces of the program are agent faces) stops when its plan has a forced removal, or a published note that would lose a file under a guard (`guardedAttachments`), that `--accept <path>` (or the key `accept` of the selection file) does not name (rule 10 of "The edits of the guards"). Name a path only when the author named that note; else the author publishes the plan in the publication center. The next plan shows every event since the last publication in its key `edits`, and `status` shows the open proposals in its key `proposals`. An edit by hand of `configuration.json` or of the property is not logged.
    - `unlock --content-store <folder>` removes the lock of the device that a publication left when it stopped halfway (a crash, a power cut), and writes `{"removed": true}` or `false`. Run it only when no publication runs. The next `plan`, `publish` or `takedown` puts the copy back from the run journal.
    - Exit codes: 0, and 1 for an error. `publish` and `unpublish` also end with 1 when the report names a note that was left out, and `takedown` when the attachment storage gave a warning. The report is then written first.
    - `status`, `plan`, `publish` and `unpublish` read the rename journals of the folder `--renames <folder>`, by default `.obsidian/plugins/dsebastien-vault-publish/renames` in the vault (R66). Each publication applies the new lines and writes `renames.json` in the content store: how many lines of each journal it read, so a line is applied one time. A deny list entry that names no folder stops every run, and the message names the new path of that folder when a line of a journal moved it (PUB-91). The commit message also counts the moves (`N moved`).
    - `--content-store` is the copy of the content store on this device: a git clone whose `origin` is the content store. The plans, the lock of the device and the run journal are stored in its git folder (`.git/vault-publish/plans/`, `lock`, `journal.json`): on the device, never in a commit, never in the vault. One publication runs at a time on a device: `publish` takes the lock, and `status` and `plan` stop while it is there.
    - `plan` and `publish` fetch the content store first and stop when the copy is behind it, with a message that says to pull (`git pull --ff-only origin main`): a copy that did not pull would keep a note under a guard live (issue 70). Without a network, `plan` uses the last fetch and `publish` stops. `status` reads no network: its key `behind` says how far the copy is behind at the last fetch, and the program then writes a warning on its error output, with exit code 0.
    - The copy must be the root of its own git repository, with an `origin`, and its last commit must hold `configuration.json`, else the program stops (R67): a wrong folder, or a clone of another repository, must never read as a content store with an empty deny list. A new content store gets its configuration in its first commit. `configuration.json`, `manifest/`, `renames.json` and `edits.json` in the copy must be the files of its last commit, else the program stops. So after an edit of the deny list by hand, commit `configuration.json` and push it before the next run: the message of the program says so. It proposes a push only when the push would change `configuration.json` alone and not remove it (it reads the difference with `origin/main`, not the names of the files in the commits), and it proposes to put back the manifest, which the tool alone writes. A publication stages and commits only the files that it wrote, also when a rule of the store ignores them.
    - `--attachment-storage` is the folder that stands for the object storage of the host, until the slice of the hosting gives the tool an object storage and its credential (OPEN-12 of the spec). Its files are named by the SHA-256 of their bytes. The program does not check the folder first: a publication with no upload never needs it, a takedown only deletes from it, and a note whose upload fails is left out and reported.
    - When the commit fails or the push is refused (another device pushed first), nothing is published: the program takes its commit back and puts every file of the publication back as it was, deletes the uploads of the run that no published note uses, the copy is as it was before, and no property is written in the vault. The author then pulls (`git pull --ff-only origin main`) and makes a new plan: the tool never pulls by itself and never forces a push. A run that stops halfway is put back by the next `plan`, `publish` or `takedown`, after `unlock` (see "Failure cases" in `Canonical Form.md`).
    - Every git command of the tool reads paths as they are written (a note name can hold `[` or `*`) and converts no line end, whatever the settings of the machine say. The one exception is the comparison of the copy with its last commit, which converts line ends as the copy converts them, and also compares the bytes of each file by its hash, with no filter of git (a file with Windows line ends is the same file). The paths of a publication go to git on its standard input, so the number of notes of one publication has no limit of the system, and the folder of the copy can be a relative path.
    - A note is read from the vault only by its exact path: each part must be a name of the folder listing, with the same letter case, and a symbolic link is not a file of the vault. Each run lists each folder of the vault one time and keeps the listing until its end, so a scan takes a time that grows with the number of notes (issue 69). The kind of each part of a path is read again before the note is read.
- In TypeScript the edits of the guards are `guards`, `edit`, and the decisions of the author `confirmProposal` and `rejectProposal` (face `plugin` only) of `apps/plugin/src/publishing/tool.ts`, with the log in `edits.ts` (issue 42).
- In TypeScript the same operations are `status`, `plan`, `publish`, `unpublish` and `takedown` of `apps/plugin/src/publishing/tool.ts`. They take a device (`ports.ts`): a vault, a content store, an attachment storage and the local store of the device (the plans, the lock and the run journal). `unlock` removes the lock. Each operation asks the vault for a vault of its run (`forRun`), which keeps the folder listings of that run only: a device lives longer than a run, in Obsidian and in the tests. `publish`, `unpublish` and `takedown` also take the time of the run, the name of the device and the face. `node/device.ts` gives a device from three folders (the vault, the copy of the content store, the attachment storage), with the `git` program of the system.
- Both implementations read the properties of a note as lines of text, with the rules of `documentation/Canonical Form.md`, and use no YAML library.
- TypeScript: `apps/plugin/src/publishing/`. Rust: `cli/src/`. The Rust program uses `clap` for its commands and `serde_json` for data. The feature `preserve_order` of `serde_json` stays off: the canonical form needs sorted keys.
- `documentation/Canonical Form.md` is the written canonical form. `fixtures/canonical/` holds its shared cases: `cases.json` (data), `properties.json` (the properties of a note), `links.json` (the links of a note), `images.json` (the size of an image), `queue.json` (scenarios of the publication queue) and `mcp.json` (the messages of the MCP server of the tool, with a stand-in for the operations).
- `parity/harness.ts` builds the Rust program with `cargo build --locked` and asks cargo where the program is. `parity/*.spec.ts` compare the bytes of both implementations.
- ESLint refuses an import of `obsidian` and of the plugin code in `apps/plugin/src/publishing/` (`no-restricted-imports`).
- The Rust program writes its output with one write and a flush. A reader that closed the pipe is not an error. Another failure of the write gives exit code 1 with a message. Exit codes: 0 for success, 1 for an error, 2 for wrong arguments.
