New requirements of round 2:

1. **Link cards**. A paragraph that starts with `LINK:` (or `LINKS:`) followed by a URL, a Markdown link, or a list of URLs and wikilinks becomes a card, as on the main site. About 800 public notes use this. A line with only `![](<YouTube URL>)` becomes a video card (about 100 notes).
2. **Reading progress bar** on all pages, as on the main site.
3. **SEO and visibility in AI answers are of critical importance.** Requirements: `documentation/research/2026-11-17-seo-and-ai-search.md`.
4. **Analytics**: a major improvement of the Plausible setup. The author wants to know what works, what does not, and what leads to sales.
5. **Inspiration**: the theme of the main site and the store are explored in depth: `documentation/research/2026-11-17-existing-sites-inspiration.md`.
6. **Featured content**: a way to put notes or parts forward, driven by properties of the notes. An idea for a later wave (GitHub issue).
7. **RSS feeds and sitemaps** are required, with the feeds and sitemaps of the theme of the main site as the model (its filtered feeds per topic, its sitemap structure). Stated again by the author at the end of the session. The research files cover both: the requirement list of the SEO research (section F) and the feed and sitemap items of the exploration of the existing sites.
8. **Ideas recorded as GitHub issues at the end of the session**: a login through a Knowii account with OAuth for the limited parts (issue 1), a reader mode inspired by Obsidian Web Clipper (issue 4), Obsidian Web Clipper templates for the notes website and for the main website (issue 5).

Findings of the exploration of the existing sites that need a decision (`documentation/research/2026-11-17-existing-sites-inspiration.md`):

1. **Canonical direction per note type**. Decision D24 says that articles and newsletters point their canonical URL to the main site. On the main site today, news posts name the notes URL as their canonical URL, and articles name themselves. So the rule must be set per note type: news notes are canonical on the notes site, articles on the main site.
2. **`Ctrl+G`** is "find next" in browsers. Proposed guards: not inside a field, no extra modifier key, and the site leaves the key to the browser after a `Ctrl+F` on that page.
3. **Link cards**: one card per URL of a `LINK:` block, or one card per block as the Ghost Publish plugin does today. And for a wikilink whose target is not live: plain text, or nothing.
4. **Link cards and images**: show a preview image of the other site, stored locally, or only an icon and text.

Facts from the private analyses that shape these questions (numbers stay private):

1. The author does not hold back changed notes, but does hold back new notes. Nothing publishes without the author today.
2. Search engines index about 1 percent of the notes today, and search traffic fell sharply during 2026, before the large media import. Media notes bring no search traffic. Permanent notes bring most of it.
3. Ad clicks can be measured since the goal was added (R9). Every click comes from the ad strip at the end of a note.
4. Some properties of media notes and person notes hold data that should not be public. Some titles of private notes show as plain text. A few notes hold full transcripts of recordings that are sold.

Findings of the first redirect list that the resolver and the tests must cover:

1. Old URLs exist with a note name that is cut at a dot, and with a tracking query that is encoded into the path. The resolver needs a rule for both.
2. Most "soft 404" examples of the search engine are canonical URLs of published notes. The cause is how the current site renders, not dead URLs.
3. Many dead URLs are former paths of product documentation under two former folders. One prefix rule can cover them.
4. Some notes that are not published are folder notes that still get visits. They need a decision: a target, or "gone".
5. The analytics tool shows paths decoded, so the parity test must compare the decoded form.
6. The list uses the status codes of rule U4 of spec v1. The SEO research proposes other codes (its item 174). The script follows the decision of the author when it exists.

## Consequences for spec v2

1. The blog and store sections leave the spec. The codebase stays open to them, but nothing is planned or built for them here.
2. Stories of section 8 with the section "B" or "St" leave. Story 102 (each article exists one time) stays as a canonical URL question: articles and newsletters exist on the notes site and on the main site.
3. The publishing tool is on the critical path of the switch: the first version must do queue, select, publish, unpublish and takedown.
4. Decision D42 is final, not "for now": no shorter URL form is planned.
5. Decision D46 removes the `noindex` rule. The quality of thin pages still matters for search engines, so generated descriptions and the "my take" layout stay in the plan.
6. The stats site keeps its own host (decision to confirm in round 2).
7. The agent-facing tools and the remote MCP server join the first release. The MCP server is a running service, so the hosting decision must cover it.
8. The command palette and several ad positions join the first release.
9. The hosting choice removes the own server from the first release. The resolver, Markdown on request and the remote MCP server run at the edge. The resolver stays plain TypeScript, so that the exit path stays open.
10. Renames need safeguards: a journal that survives a restart, a pairing step for renames that the plugin did not see, and a test for a folder rename that touches many notes.
