New requirements of round 2:

1. **Link cards**. A paragraph that starts with `LINK:` (or `LINKS:`) followed by a URL, a Markdown link, or a list of URLs and wikilinks becomes a card, as on the main site. About 800 public notes use this. A line with only `![](<YouTube URL>)` becomes a video card (about 100 notes).
2. **Reading progress bar** on all pages, as on the main site.
3. **SEO and visibility in AI answers are of critical importance.** Requirements: `documentation/research/2026-11-17-seo-and-ai-search.md`.
4. **Analytics**: a major improvement of the Plausible setup. The author wants to know what works, what does not, and what leads to sales.
5. **Inspiration**: the theme of the main site and the store are explored in depth: `documentation/research/2026-11-17-existing-sites-inspiration.md`.
6. **Featured content**: a way to put notes or parts forward, driven by properties of the notes. An idea for a later wave (GitHub issue).
7. **RSS feeds and sitemaps** are required, with the feeds and sitemaps of the theme of the main site as the model (its filtered feeds per topic, its sitemap structure). Stated again by the author at the end of the session. The research files cover both: the requirement list of the SEO research (section F) and the feed and sitemap items of the exploration of the existing sites.
8. **Ideas recorded as GitHub issues at the end of the session**: a login through a Knowii account with OAuth for the limited parts (issue 1), a reader mode inspired by Obsidian Web Clipper (issue 4), Obsidian Web Clipper templates for the notes website and for the main website (issue 5).

Everything that was not asked in round 4 (the decisions of the SEO and AI search research, the features of the existing sites, the design, the license of the note content, the remaining decisions of the publishing tool study) is in round 5.

Findings of the exploration of the existing sites that needed a decision (`documentation/research/2026-11-17-existing-sites-inspiration.md`). All four are decided in round 5 (items 285, 147, 96 to 99 with 112, and 105h). The author did not follow the proposal of finding 1:

1. **Canonical direction per note type**. Decision D24 says that articles and newsletters point their canonical URL to the main site. On the main site today, news posts name the notes URL as their canonical URL, and articles name themselves. So the rule must be set per note type: news notes are canonical on the notes site, articles on the main site.
2. **`Ctrl+G`** is "find next" in browsers. Proposed guards: not inside a field, no extra modifier key, and the site leaves the key to the browser after a `Ctrl+F` on that page.
3. **Link cards**: one card per URL of a `LINK:` block, or one card per block as the Ghost Publish plugin does today. And for a wikilink whose target is not live: plain text, or nothing.
4. **Link cards and images**: show a preview image of the other site, stored locally, or only an icon and text.

Facts from the private analyses that shape these questions (numbers stay private):

1. The author does not hold back changed notes, but does hold back new notes. Nothing publishes without the author today.
2. Search engines index about 1 percent of the notes today, and search traffic fell sharply during 2026, before the large media import. Media notes bring no search traffic. Permanent notes bring most of it.
3. Ad clicks can be measured since the goal was added (R9). Every click comes from the ad strip at the end of a note.
4. Some properties of media notes and person notes hold data that should not be public. Some titles of private notes show as plain text. A few notes hold full transcripts of recordings that are sold.

Findings of the first redirect list that the resolver and the tests must cover:

1. Old URLs exist with a note name that is cut at a dot, and with a tracking query that is encoded into the path. The resolver needs a rule for both.
2. Most "soft 404" examples of the search engine are canonical URLs of published notes. The cause is how the current site renders, not dead URLs.
3. Many dead URLs are former paths of product documentation under two former folders. One prefix rule can cover them.
4. Some notes that are not published are folder notes that still get visits. They need a decision: a target, or "gone".
5. The analytics tool shows paths decoded, so the parity test must compare the decoded form.
6. The list uses the status codes of rule U4 of spec v1. The author accepted the codes of the SEO research in round 5 (its item 174): the script must change to them.

New requirements of round 5:

1. **The interactive part of a publication must be fast.** To see what can be published, to select and to start the publication must be quick, and must never block or slow Obsidian. This is a major reason for the project. The work behind it can take longer, as long as it runs in the background. A git commit and push should be enough to put content online. A budget of under 1 minute from the click to live was named first. The author then said that this time matters less than the interactive part.
2. **Products.** Everything about products (ads, buy box, offer map, live prices) needs a strong relationship with the store website, which stays a separate thing (ADR 0001).
3. **Shape of the publishing tool.** It starts from the author's Obsidian plugin template. It includes a command line program, an MCP server and a skill, so that an AI can drive the whole process. What the MCP server can do, the command line program can do, and the reverse. The command line program follows the model of the one of the Obsidian Starter Kit plugin: Rust, cross-platform, Linux and Windows for now.
4. **Breadcrumbs** on all pages, if possible, to ease navigation. The folder notes of the author (a note with the name of its folder) can be the homes of parts of the site. This reopens item 184 (the breadcrumb follows the type hub). The author reviews his folder notes (private task note).
5. **PKM Library.** This paid product of the author becomes a first-class part of the site. Its content is converted into notes of the vault. It waits for the login (issue 1), because customers must log in and the site must know what they can see. The same access applies at the MCP server (issue 7).

## Consequences for spec v2

1. The blog and store sections leave the spec. The codebase stays open to them, but nothing is planned or built for them here.
2. Stories of section 8 with the section "B" or "St" leave. Story 102 (each article exists one time) stays as a canonical URL question: articles and newsletters exist on the notes site and on the main site.
3. The publishing tool is on the critical path of the switch: the first version must do queue, select, publish, unpublish and takedown.
4. Decision D42 is final, not "for now": no shorter URL form is planned.
5. Decision D46 removes the `noindex` rule. The quality of thin pages still matters for search engines, so generated descriptions and the "my take" layout stay in the plan.
6. The stats site keeps its own host (decision to confirm in round 2).
7. The agent-facing tools and the remote MCP server join the first release. The MCP server is a running service, so the hosting decision must cover it.
8. The command palette and several ad positions join the first release.
9. The hosting choice removes the own server from the first release. The resolver, Markdown on request and the remote MCP server run at the edge. The resolver stays plain TypeScript, so that the exit path stays open.
10. Renames need safeguards: a journal that survives a restart, a pairing step for renames that the plugin did not see, and a test for a folder rename that touches many notes.
11. The allow list per property key is not decided (issue 6). Until it is, spec v2 cannot assume that a property is dropped. The author accepts that collection data (purchase, sale, storage) is public.
12. The deny list of the privacy gate starts from the excluded folders of the Obsidian Publish configuration, plus the folders of decision Q5b. A note that was never published stays private until the author selects it (ADR 0008).
13. The transcript notes stay public. Whether they can be part of a bulk output belongs to decision D47.
14. The executor of the MCP `execute` tool is not decided (issue 7). The hosting prototype must wait for it, or test both executors.
15. Person notes: every property is public and every note is indexed, until an allow list exists. The structured data of a person note can then use the properties that exist.
16. Nothing in the first release depends on Obsidian Publish after the switch. The tools of the author that read it move to the new publishing tool.
17. ADR 0008 replaces the intent model of ADR 0002. Spec v2 must rewrite every place that says "the property is the intent": the publication queue lists candidates, the tool writes the property after a publication and removes it after a removal, and the reconciliation that the current template does becomes a job of the tool. The name of the ignore property is open.
18. The eligibility test of the Ghost Publish plugin stays valid after the switch, because the property still means "live".
19. The tool never trusts the value of the `public_note` property in a note. It corrects the value at the end of each publication from the manifest. Spec v2 needs a test for the case "a new note carries the property with the value true and was never published": the tool does not publish it, and it corrects the property.
20. ADR 0010: a note that also exists on the main site names the main-site URL as its original. The site needs the real URL of each post (articles, newsletters and news posts). The Ghost Publish plugin and the existing news posts change before or at the switch, never after. The switch gate gets a test: for each such note, both sites name the same URL. These notes are not expected to rank on the notes host, so the success metric (item 195) must count them apart.
21. ADR 0009: the cleaned note, the publication plan and the manifest must be identical in the two implementations. Parity tests on the fixture vault block a release. Decision D17 ("one publish core with two hosts") and the command line handlers of R5 are rewritten for this shape. The headless slice (K1) is the Rust command line program.
22. Performance of the publishing tool is a release criterion, like the page budgets (D30). Spec v2 needs budgets for "time to see the plan" and "time to start a publication", measured on the real vault, and the rule that no step blocks Obsidian. The build runs behind the scenes. A prototype decides its place (D43), with CI as the preferred one.
23. The first version of the tool has no confirmation limits (K6, issue 9). Decision D12 lets an agent apply a plan "under the limits", so spec v2 must say what an agent may apply alone until limits exist.
24. The analytics receive the text of every search (item 292). A search text can hold personal data, so the "what this site records" page must say it plainly.
25. Page titles (item 183) are a design item of spec v2: the source of the title (the `title` property or the file name), the pattern per note type from the type definitions, and the site name from the mockups.
26. Breadcrumbs: spec v2 needs a rule for a folder level with a folder note, for a folder level without one, and for generated pages. The canonical URL already holds the folder levels (ADR 0005).
27. Buy box, offer map, live prices and the ad format all read the store catalog. The shape of that catalog is a contract with a test that blocks a release, and a change on the store side must be visible to this project.
28. The PKM Library and the access for customers at the MCP server are not part of the first release. They depend on the login of issue 1.
29. The first release has three newsletter positions: the bar, one position inside long notes, and the dialog for a reader who leaves.
30. Keyboard: `/`, `Ctrl+K` and `?` for the palette and the shortcuts sheet, and the sequence `g` then `g` for the graph. No key of the browser is taken.
31. The AI disclosure follows the `ai_generated` property of a note. The property exists on more note types than the wiki articles, so the rule is per note, not per type.
32. No AI crawler is blocked at the first release (items 188 and 189). The training rule of D33 for content of other people is then stated in the policy files only, and has no technical effect for these crawlers.
33. Licenses: CC BY-NC-SA 4.0 for the author's own text, all rights reserved for product documentation and transcripts, and no license for material of other people. The license line of a note needs a rule per note type or folder.
34. The redirect list and the resolver use 301 for syntax variants and bare file names, and 302 for aliases (item 174). Rule U4 of spec v1 changes.
